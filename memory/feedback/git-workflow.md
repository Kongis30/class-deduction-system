# Git 协作与发布约定

## 唯一主分支

- `main` 是项目唯一主分支，也是唯一允许部署到生产环境的代码来源。
- `main` 必须始终保存最新、完整、可构建的项目代码；后端、前端、测试、数据库迁移和必要文档必须保持在同一条提交历史中。
- 不使用 `release/*`、`online`、临时 worktree 或历史 `deploy/` 构建包作为生产部署来源。

## 新功能开发

- 小范围、低风险改动直接在 `main` 上完成，例如 UI 样式微调、文案调整或局部小修复；确认工作区里其他未提交改动的归属，不要混入无关内容。
- 大功能、较大或高风险修复、跨模块改动，从最新 `main` 创建临时本地分支，例如 `codex/<feature-name>`。
- 一个会话或一个并行任务只负责一个明确的功能分支和范围；不要让多个会话分别修改同一功能后各自提交不完整的半成品。
- 完成功能后，必须把相关后端、前端、测试、迁移和文档作为一个完整变更验证并提交，不能只提交其中一部分。
- 大功能分支验证通过后，将其合并回 `main`；确认合并后的 `main` 仍可构建、测试通过，再删除临时分支。
- 若发现其他会话有未提交改动，不覆盖、不回退、不擅自混入；先明确归属，必要时暂停并由一个集成方统一合并。

## 提交要求

- 提交以完整可解释的功能节点为单位，避免只提交“部署标记”、单独生成文件或无法独立工作的半个功能。
- 每次提交前检查 `git status`、分支和最近提交，确认没有遗漏同一功能涉及的文件。
- 不把 dirty worktree、未提交文件或另一个会话的修改作为发布内容。

## 生产部署要求

- 部署前先将已完成的临时分支合并到 `main`，然后以 `main` 的最新 commit SHA 作为唯一发布版本。
- 从该 commit 创建干净的临时 worktree，重新编译完整后端 jar 和前端 dist；禁止直接复用旧 `deploy/` 包或旧分支构建产物。
- 后端、前端、数据库迁移和版本标识必须来自同一个 `main` commit；部署清单记录完整 commit SHA、构建产物校验和及迁移执行结果。
- 部署前要求构建 worktree clean；部署后核对线上版本 SHA、jar/dist 校验和、服务状态、启动日志、登录接口及核心业务接口。
- 如果 `main` 不是最新完整代码，先完成分支合并和验证，不能为了上线临时绕过主分支。
