# E2E 长期运营业务流程检查清单

## 1. 目的和执行原则

本清单用于重建 Playwright E2E，不以“按钮可点击”作为通过标准，而是模拟机构持续使用后的完整业务结果。

每个场景都必须同时满足：

1. 关键用户动作通过当前页面完成。
2. 页面显示的订单、余额、课次、状态和提示正确。
3. API 和数据库事实数据与页面结果一致。
4. 失败操作不产生半成品数据，也不改变既有正确数据。
5. 每个场景使用独立测试标记并在结束后清理全部派生数据。

允许 API/数据库的范围：

- 创建测试前置数据，例如校区、课程、老师和价格行。
- 查询订单、付款、课包、课次、台账、工资和冲突结果。
- 清理测试数据。

不允许 API/数据库替代的范围：

- 报名、后续付款、课程选择、排课调整、老师确认、管理员终确认、教室后补、工资创建和工资确认。
- 任何页面没有入口时，不允许 API fallback 把该场景标记为“UI E2E 已通过”；必须标记为产品缺口。

## 3. 测试数据和断言基线

### 3.1 固定数据规范

- 每个 scenario 使用唯一 `E2E_LONG_<scenario>_<timestamp>` 标记。
- 每个并行逻辑场景使用独立学生、老师、教室和课程，避免数据串扰。
- 所有金额以两位小数断言；所有课时以 0.5 小时为最小单位断言。
- 1 对 1 的内部半小时单位、对外小时显示、`hour_ledger` 变化和课包余额必须同时断言。
- 所有页面操作先断言页面可见的成功、警告或错误提示，再检查 API/数据库。

### 3.2 关键不变量

- `订单余额 = 应收 - 付款流水净额`。
- `课包剩余 = 总课时 - 已扣课时`。
- `课时台账累计变化 = 课包已用课时变化`。
- `管理员终确认前，不扣课、不写最终台账、不进入老师待支付`。
- `老师付款只包含管理员终确认且未结算的实际完成课次`。
- 历史订单、付款、收据和工资快照不被后续价格、费率或档案修改反写。

## 4. 核心长期运营场景

每项初始状态均为 `[ ] 未执行`。通过后记录运行日期、脚本路径和证据。

### A. 初始配置和报名准备

- [ ] `E2E-A01` 新建课程产品后，管理员在 Prices 中为不同年级、时长和价格建立有效价格行；Registration 按“课程 -> 年级 -> 时长/时段 -> 自动报价”联动。
- [ ] `E2E-A02` 停用价格行或课程产品后，Registration 不再允许选择；历史报名和收据仍展示原快照。
- [ ] `E2E-A03` 价格行缺失时，Registration 给出明确入口到 Products 或 Prices，不允许以 0 元保存。
- [ ] `E2E-A04` 创建 GROUP 产品后可完成班课报名；创建 ONE_ON_ONE 产品后可选择老师和首课时间。
- [ ] `E2E-A05` 同一老师、学生或教室在相同时段创建冲突计划时，页面显示冲突对象和时间，数据库无新增课次。

### B. 新学生报名、账号、收据和首次付款

- [ ] `E2E-B01` 新学生通过 Registration 完成 1-on-1 报名：创建学生、订单、订单明细、课包、首课、付款和收据。
- [ ] `E2E-B02` 新学生 1-on-1 报名后自动创建学生账号；结果页与右上角提示展示用户名、账号创建状态和初始密码规则。
- [ ] `E2E-B03` 新学生班课报名不创建学生登录；页面结果和右上角提示明确说明该规则。
- [ ] `E2E-B04` 首次报名使用多笔、不同支付方式付款；每笔付款日期、方式、金额正确，订单已收和余额正确。
- [ ] `E2E-B05` 首次报名只付部分款；结果页显示余额，Students 历史和 Data Summary 显示相同待收金额。
- [ ] `E2E-B06` 报名输入超额付款、空支付方式、缺少 Other 说明、折扣超额、无老师或无价格时，页面提示具体错误且不产生任何订单或付款。
- [ ] `E2E-B07` 报名成功后可打印并从 Students 历史回看同一份报名表与收据快照。

### C. 老学生再次报名和分期付款

- [ ] `E2E-C01` 老学生再次进入 Registration，以“姓名 + 主家长电话”识别并复用学生档案，不创建重复学生。
- [ ] `E2E-C02` 老学生再报新的 1-on-1 课程后，生成新的订单和新的课包；旧课包余额、旧订单快照和旧课次不被修改。
- [ ] `E2E-C03` 老学生已有账号时再次报 1-on-1，复用账号、不重置密码；页面结果和通知明确显示“账号已复用”。
- [ ] `E2E-C04` 从 Students 历史为旧订单补款，验证付款流水、订单余额、付款状态、Data Summary 和收据入口一致。
- [ ] `E2E-C05` 同一订单多课程时补一笔款，不得将同一笔金额重复计入多个课包的实收或余额。
- [ ] `E2E-C06` 同一学生重复加入同一个有效班级被阻止；同一学生报名不同课程或新周期时允许并保留两条独立历史。

### D. 1-on-1 固定排课、实际课时和未来计划平衡

- [ ] `E2E-D01` 1-on-1 报名后创建固定每周 2 小时计划，课包总时长、首课和未来课次总量可追踪。
- [ ] `E2E-D02` 老师确认计划 2 小时、实际 2 小时课次后，管理员终确认：扣 2 小时、写台账、未来排课不变化、进入待支付。
- [ ] `E2E-D03` 老师确认计划 2 小时、实际 1.5 小时课次后，管理员终确认：本次只扣 1.5 小时，课时台账扣 1.5 小时，最后一个未来未确认课次从 2 小时延长为 2.5 小时，课包预计结束日期重新计算。
- [ ] `E2E-D04` 计划 2 小时、实际 1.5 小时时，未来最后一节延长 0.5 小时若与学生、老师或教室冲突，管理员终确认必须失败；课次、课包、台账和工资候选均保持确认前状态。
- [ ] `E2E-D05` 计划 2 小时、实际 2.5 小时时，本次扣 2.5 小时，系统从最后一个未来未确认课次减少 0.5 小时；若不足则从尾部取消或减少多个未来课次，且总课时守恒。
- [ ] `E2E-D06` 实际课时变化但没有未来可调整课次时，页面显示“需要调整未来排课/续费/拒绝确认”的明确下一步，且不写半成品终确认。
- [ ] `E2E-D07` 临时调整本周课次的时间、老师、教室或时长时，只修改本周 occurrence，不修改 recurring rule，并写入 adjustment log。
- [ ] `E2E-D08` 已确认课次不能再调整；对已确认课次的调整失败不改变课次、余额和台账。

### E. 1-on-1 双确认、异常课次和恢复

- [ ] `E2E-E01` 老师初确认 Completed 后状态为 `PENDING_ADMIN`；课包余额、最终台账和待支付工资均不变化。
- [ ] `E2E-E02` 管理员终确认 `PENDING_ADMIN` 后状态为 `CONFIRMED`；只执行一次扣课、台账和待支付资格。
- [ ] `E2E-E03` 管理员直接确认课次时，页面和数据结果与双确认终态一致，并遵守权限边界。
- [ ] `E2E-E04` Formal Leave 不扣学生课时、不产生老师工资，且生成或可追踪补课/顺延结果。
- [ ] `E2E-E05` No Show 按规则扣学生计划课时、不产生老师工资，课时台账原因明确。
- [ ] `E2E-E06` 管理员驳回老师初确认后，课包余额、台账和工资资格不变；老师能在当前 UI 中重新确认，随后管理员可终确认。
- [ ] `E2E-E07` 同一 lesson record 重复老师确认、重复管理员确认或重复付款时，系统拒绝重复操作且不重复扣课或计薪。
- [ ] `E2E-E08` 课包余额不足时，确认操作被阻止，页面能说明不足原因，课包和台账不变化。
- [ ] `E2E-E09` 剩余课时小于等于两节默认课时后，1-on-1 页面和 Data Summary 都显示一致的续费提醒。

### F. 班课长期使用

- [ ] `E2E-F01` 班课产品和价格准备完成后，Registration 可完成首次班课报名并生成班级资格。
- [ ] `E2E-F02` 班课学生按次购买或按月报名时，应收、已收、有效期、可上课次数和班级汇总进度正确。
- [ ] `E2E-F03` 班课老师初确认和管理员终确认均可通过当前 UI 完成；学生剩余次数、班级进度和老师工资资格一致。
- [ ] `E2E-F04` 班课中途加入学生不改写既有学生的购买次数、历史付款或课程进度。
- [ ] `E2E-F05` 班课学生到期、取消或退款后，不再出现在有效班级资格或未来课次统计中；历史订单和退款流水仍可追溯。
- [ ] `E2E-F06` 班课课次调整、教室冲突和老师冲突在 UI 中有可执行提示，失败时不改变排课数据。

### G. 教室、日历和冲突闭环

- [ ] `E2E-G01` 报名时未分配教室的 1-on-1 或班课，出现在 Classrooms 的 Pending assignments。
- [ ] `E2E-G02` 在 Pending assignments 选择教室并保存后，Room Calendar 出现该课次，待分配列表同步消失。
- [ ] `E2E-G03` 为同一教室重叠时段分配课次时，保存失败并显示冲突时间和相关课程。
- [ ] `E2E-G04` Teacher Calendar、Student Calendar、Room Calendar 对同一课次显示相同开始、结束、老师、学生和教室。
- [ ] `E2E-G05` 1-on-1 实际少上导致未来最后课次延长后，Room Calendar、Teacher Calendar、Student Calendar 同步显示调整后的结束时间。

### H. 退款、取消和历史事实

- [ ] `E2E-H01` 未上课的整单全额退款：生成负向付款流水，订单状态、余额、课包/班级资格、未来课次、Data Summary 和历史收据口径一致。
- [ ] `E2E-H02` 取消未付款订单：不生成退款流水，不影响其他订单、课包和学生历史。
- [ ] `E2E-H03` 已有部分付款的整单退款：只退实际已收金额，余额归零，不能多退。
- [ ] `E2E-H04` 部分退款、按课程退款、已消课退款和 tuition credit 当前未实现时，页面必须不提供会写错数据的伪入口，并明确转人工处理。
- [ ] `E2E-H05` 后续修改课程价格、学生资料、支付方式或老师费率后，历史订单、付款、收据和已结算工资保持原快照。

### I. 老师费率和工资结算

- [ ] `E2E-I01` 设置老师-课程费率后，后续管理员终确认的 Completed 课次按实际课时和当前费率进入待支付。
- [ ] `E2E-I02` 修改费率只影响未结算课次；已创建的工资单项目保留创建时的费率和金额。
- [ ] `E2E-I03` 无费率或 0 费率课次显示明确警告；系统按已定义规则阻止或要求显式继续，不能静默产生意外工资。
- [ ] `E2E-I04` 按日期范围创建老师付款时，只选择该区间内已终确认、未结算课次。
- [ ] `E2E-I05` 创建并确认工资单后，课次不再出现在待支付列表；付款历史、明细、金额和时间可追溯。
- [ ] `E2E-I06` 被驳回、Formal Leave、No Show 或退款关闭的课次不进入老师待支付。

### J. 数据整理、权限和用户体验

- [ ] `E2E-J01` Data Summary 与 Students、Orders、Course Packages 对应收、已收、余额、付款状态和课时显示一致。
- [ ] `E2E-J02` Data Summary 的余额、低课时、临期、接送和待复核提醒可以从页面跳转或定位到对应业务记录。
- [ ] `E2E-J03` Admin tools 的 Guide、Courses、Finance、People 和 System 页面均可达，且当前名称与实际页面标题一致。
- [ ] `E2E-J04` 报名保存、账号创建/复用、排课冲突、终确认成功/失败、补款、退款和工资结算都有明确用户可读提示。
- [ ] `E2E-J05` TEACHER 只能看到自己的学生和课次，只能初确认自己的课次；STUDENT 只能查看自己的课程和日历。
- [ ] `E2E-J06` 直接访问受限路由或调用越权 API 时，前端跳转和后端权限都能阻止访问。
- [ ] `E2E-J07` 窄屏下 Registration、1-on-1、Classrooms、Data Summary 和 Guide 不压缩变形，保留横向或纵向滚动。

## 5. E2E 重建顺序

1. 删除旧 `system-regression` 和依赖旧 Enrollment Orders 主流程的脚本。
2. 先建立 Registration 场景：新学生、分期付款、账号创建、老学生再报。
3. 建立 1-on-1 全链路：固定排课、双确认、2h/1.5h 平衡、冲突回滚。
4. 建立班课、教室后补和日历一致性。
5. 建立退款、工资、报表和权限长期场景。
6. 每完成一个场景，运行单文件、相关目录和全量 E2E；记录失败为产品缺口或实现缺陷，禁止 API fallback 掩盖。

## 6. 通过标准

只有以下条件同时满足，场景才可以勾选通过：

- 用户可以从当前页面完成关键操作。
- 成功和失败都有明确页面反馈。
- API、数据库和页面数据相互一致。
- 测试数据可完全清理。
- 测试不依赖旧路由、旧名称、固定等待时间或未声明的 API fallback。

## 7. 代码审查与单测证据

以下内容仅表示代码逻辑和定向单测已覆盖，不代表对应 E2E 场景通过：

- 课程和首课时长统一限制为 0.5 小时粒度，课程同日时段禁止重叠。
- 班课进度只统计管理员终确认记录；重新报名按当前报名有效期计算已用次数。
- 班课确认限制结果状态，并校验实际时间、实际课时一致；管理员空表单终确认保留老师提交的实际数据。
- 1-on-1 终确认会在扣课和写台账前校验本次实际时间对应的学生、老师和教室冲突。
- 计划课时与实际课时不一致时，未来课次调整冲突会触发事务回滚。
- 班课工资按 occurrence 选择唯一代表记录，阻止同一班课课次按多个学生重复计薪。
- 已收款订单禁止直接取消；取消订单乐观锁失败时抛错并回滚课程关闭副作用。
- 全额退款校验退款方式有效，已有上课记录时转人工审核。
- 多笔补款通过单个事务请求写入，支持每笔独立日期、经手人和备注；金额最多两位小数，Other 方式必须填写说明。
- Data Summary 课包详情直接使用后端小时值，不再重复除以 2。
- 班课报名会校验学生与已有 1-on-1、其他有效班课课次的时间冲突；冲突时整个报名事务回滚。
- 班课管理员终确认会校验实际老师、教室和每名有效学生的时间冲突。
- 教室后补会锁定目标教室，使同一教室的冲突检查和写入串行执行；课次乐观锁更新失败时整体回滚并提示重试。
- 1-on-1 报名允许老师和教室暂不安排；管理员可在课程记录中为单次未确认课分配老师和教室，冲突校验通过后学生 Calendar 同步显示该安排。
- 前端写请求（报名、付款、退款、确认）不再自动重试，仅 GET/HEAD 等幂等读取重试，避免网络丢包导致重复入账或扣课。
- SMTP 通知配置控制器限定仅管理员可读写与触发测试邮件，杜绝任意登录用户篡改发件配置。
- 通用订单更新禁止修改订单状态，取消和退款必须分别走 cancelOrder 和 refundOrder，防止绕过已收款限制与资格撤销。
