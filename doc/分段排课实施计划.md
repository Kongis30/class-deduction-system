# 分段排课实施计划

状态：团课阶段 1–4 已进入实现；1-on-1 阶段 5–6 待团课稳定后实施。依据[团课分段排课功能设计](./团课分段排课功能设计.md)及[1-on-1 分段排课交互设计](./1-on-1分段排课交互设计.md)。图示需求首先对应**团课 Actual class 的多段日期/时间**，因此先完整交付团课，再独立交付 1-on-1；不同时重写两套排课服务。

## 1. 顺序与发布原则

采用“兼容旧数据 → 统一日期计算 → 安全预览和保存 → 所有入口的 UI → 上下游验收”的顺序。一个阶段结束不等于可以上线：团课至少完成第 1–4 阶段及其验收后，才向用户开放分段保存。1-on-1 在团课稳定后按第 5–6 阶段实施，不复用团课的额度和老师交接规则。

现有 `ClassScheduleDates` 按所有 slot 的星期并集计算日期，`ClassGroupServiceImpl.updateClassSchedule` 会替换旧 slot 并重建未来课次；`RegistrationIntakeServiceImpl`、`EnrollmentOrderServiceImpl`、假期处理和每日续排也会读取排课。先只改弹窗会出现“页面有空档，报名和课次仍在空档生成”的问题。因此前端分段入口必须是后端与相关读取路径完成之后的最后一步。

| 阶段 | 先决条件 | 交付结果 | 可否开放分段保存 |
| --- | --- | --- | --- |
| 0. 基线与边界核对 | 无 | 固定旧行为和受影响业务清单 | 否 |
| 1. 团课兼容数据模型 | 0 | 旧班级可按单段读取，新字段可用 | 否 |
| 2. 团课统一日期/课次计算 | 1 | 生成、报名、假期和续排识别段及空档 | 否 |
| 3. 团课预览与事务性保存 | 2 | 安全保留历史、调整课次及报名权益 | 否 |
| 4. 团课 Create/Edit UI 与验收 | 3 | 三个入口完整可用，团课可发布 | **是，团课** |
| 5. 1-on-1 规则与额度引擎 | 团课发布稳定；也可独立开发 | 多段规则可读写，余额与交接正确 | 否 |
| 6. 1-on-1 Create/Edit UI 与验收 | 5 | 1-on-1 可发布 | **是，1-on-1** |

## 2. 阶段 0：核对旧行为，建立验收基线

1. 固定两套现有模型的含义：团课 `class_group` / `class_group_schedule_slot` 与 1-on-1 的 `recurring_schedule_rule` / `recurring_schedule_slot` 不合并；确认实际班级初建后无课表时的 Create 入口、旧单周课表 Edit 回显、假期顺延和 A/B 轮换的当前结果。
2. 对照代码梳理所有实际调用路径，至少包含班课三个保存入口、团课课次生成、项目假期、报名及 Edit receipt、每日续排、单节 Adjust、消课、Data Summary、日历和 roster。形成“某个日期如何被认定为上课日”的唯一调用链，避免新增第二套判断。
3. 盘点旧数据里已有处理记录、单节 Adjust、跨老师交接、缺失 slot 引用等形态。先确定如何安全识别“不能删除的历史/例外课次”；无法识别的记录必须在 Edit 时被阻止并提示，不能猜测后重建。
4. 固定旧单段样例与图示三段样例的预期结果。图示在没有假期时为 2 + 3 + 4 节、27 小时，段间空档为零课次。这些样例成为后续各阶段的回归依据。

完成标准：旧单段的课次、报名日期、假期顺延和课包计数有可核对的基线；历史课次/调整课次的保留规则明确。

## 3. 阶段 1：团课数据与接口兼容层

1. 给 `class_group_schedule_slot` 增加可空的生效起止日期；旧数据两个日期皆空解释为班级原周期内的单段。补足稳定的逻辑课位标识或等价关联，保留旧 slot 可供历史课次、调整日志回溯，不把旧 slot 物理删除。
2. 读取接口返回按日期归组的 `scheduleSegments`，同时保留旧字段供现有页面读取。新保存请求带 `segments`；旧 `slots` 请求仅能用于尚未分段的班级。已有多段时拒绝旧格式覆盖并提示刷新。
3. 校验每段日期首尾、班级原周期边界、段间不重叠、同段时段不冲突、老师/教室有效性。旧单段数据原样读取、未修改后重新保存不得改变课次。沿用项目已有的增量建表/加列机制，保持旧服务启动后兼容读取。

完成标准：老班级、空课表班级和新多段对象都能读取；旧客户端无法抹掉已保存的分段；此时**尚不开放新保存入口**。

## 4. 阶段 2：统一团课的日期计算与下游读取

1. 将 `ClassScheduleDates` 从“星期并集”改为“日期落在生效段内且匹配该 slot 周几”的共用判断。`scheduledDays` 仍对同一天去重；同日多个时段在课次生成中仍各生成一节。无排课段的空档不生成、不可被报名日期选择器选中。
2. `ClassGroupServiceImpl.generateFutureClassOccurrences` 和每日续排调用同一判断，不各写一套分段循环。A/B 轮换仅统计本课位有效区间内的真实上课日；保持旧单段轮换结果不变。
3. 项目假期按所有段的原始上课日数（同日多时段只计一天）计算缺口；原周期后需要顺延时，按**最后一段**的周时段派生补课日期，并在预览中展示。假期新增、删除、修改与课表编辑必须得到相同的有效结束日。
4. 修改团课模型、报名、Edit receipt、按课次权益计算的日期来源；验证按月收费/月份、原收据和报名行不因排课段变化而拆分或改价。

完成标准：任一日期至多属于一个有效段，但段内可命中多个 slot；生成课次、报名日期、假期顺延与每日续排对同一班级结果一致。旧单段结果保持基线。

## 5. 阶段 3：团课预览与原子保存

1. 从现有 `updateClassSchedule` 中提取一条可复用的“计算变更结果”路径。只读预览和正式保存使用同一套日期展开、假期、资源/学生冲突与报名权益校验；正式保存在事务和现有锁下重算，不依赖客户端传回的预览。
2. 明确把课次分为**已发生/有处理记录**、**单节 Adjust 等例外**、**可替换的普通未来课次**。前两类保留原时间、老师、课时与确认状态；第三类才按新模板替换。保留课次占据原模板课位，不能因更换日期或老师再次生成重复课次。
3. 在预览里列出保留、撤销、生成课次及报名权益截止日变化。若删除未来段导致已购课次无法履约、与保留课次冲突，或旧数据无法确定单节例外归属，拒绝保存并给出具体课次原因。
4. 更新模板和普通未来课次时保留历史 slot/调整引用；并发修改需检查班级版本。失败整笔回滚，不能留下“课表更新了、报名权益仍是旧值”的中间状态。

完成标准：调整过的单节课和历史消课不消失、不重复；预览与保存课次数一致；冲突和权益不足均明确报错且数据库无部分写入。

## 6. 阶段 4：团课 Create/Edit 交互及完整验收

1. 将 `GroupCourseModelPanel.vue`、`CoursePriceOptionsView.vue`、`ScheduleAdjustmentsView.vue` 的班课课表入口接到**同一段式表单和提交模型**。无 slot 显示 Create schedule，已有 slot 显示 Edit schedule；旧单段完整回填。保留现有周时段选择及资源字段，不做第二套隐藏表单。
2. 每段卡片包含起止日期、时段、老师/科目/教室/轮换和课次摘要；提供 Add / Copy / Remove period。移动端折叠其他段；日期冲突与空档即时提示。保存前展示实际课次、假期、保留例外和报名权益变化。
3. 团课端到端核对：首次单段创建、图示三段、段间空档、同日双时段、跨段换老师/教室、A/B 轮换、单节 Adjust、已确认/待审核历史、假期增删、按月/按次报名及续报、Data Summary/roster/日历、旧客户端覆盖及并发保存。验证三个入口互相编辑后不丢字段。
4. 团课完成后先上**兼容后端**，确认旧页面照常工作，再更新三个前端入口。开始写入多段数据后，回退只能回到仍可识别分段的后端版本；不能直接回退到会把多段压平的旧服务。

发布门槛：团课回归通过，生产环境旧单段班级读写不变；图示 9 节/27 小时及空档验证通过；历史、报名、消课与假期不受影响。

## 7. 阶段 5：1-on-1 规则、额度与老师交接

1. 在 `recurring_schedule_slot` 增加可空的生效日期，旧 slot 解释为现有规则的单段；保持一个有效课包、一个当前规则及已有 `supersedesRuleId` 版本链。计划段与“编辑产生的规则历史版本”分开表示。
2. 将多个段展开为候选课次后，继续经由现有**每 slot 分配额 → 课包余额 → 学生/老师/教室冲突**流程；预览清楚显示日期容量、实际生成课时和剩余。跨段不得多用课包额度，尾课沿用现有不足整节的行为。用户原设分配额不被自动改动。
3. Edit 保留已处理、待处理及人工调整课次的时间线；沿用 slot lineage 和现有老师交接：新老师获得整个逻辑课包及未处理课次操作权，历史任课/扣课归属不改。首版不支持“预设某个未来段自动换老师”，以免造成两个老师同时拥有同一个课包入口。
4. 按团课同样顺序实现兼容读、预览/保存共用计算、旧格式覆盖保护；但不把团课假期/报名按次权益逻辑复制到 1-on-1。保持周 Adjust、暂停/恢复和 Edit receipt 续课后的账本行为。

完成标准：单段旧规则回显和保存不变；多段总生成课时与各 slot 分配额及课包余额对齐；交接后只有新老师拥有课包入口，完整 lesson records 不丢。

## 8. 阶段 6：1-on-1 交互与验收

在 `RecurringScheduleView.vue` 既有 Create Schedule / Edit Schedule 弹窗中加段卡片和预览，不新增一套排课页面。Create 显示课包可安排余额；Edit 完整回填计划并同时展示旧分配额、保留课次和拟新增课次。保存失败保留用户输入，冲突展示日期、时间、课程和老师，不展示内部 ID。

至少核对：一次创建三段，空档不排课；修改未来段但保留历史和单节 Adjust；增减分配额；编辑日期不足以排完指定额度；续课后增加新段；暂停/恢复；A 老师已消课、待处理及未来课次并存时交给 B 老师，再次 Edit 后 B 仍能看到完整时间线并处理课次。通过后再部署 1-on-1 前端入口。

## 9. 控制范围与交付清理

- 不新建第二套课包或报名，不调整收据价格/付款，不修改用户手工设置的老师分配额来“凑”课次。
- 不让单节 Adjust 改动整套模板；不让多段 UI 单独上线；不在预览与保存各实现一套日期计算。
- 每阶段清理被替代的旧日期判断、旧扁平表单分支和无用兼容代码，但保留必要的旧数据读取与 API 防覆盖逻辑；遵循仓库 `AGENTS.md` 的“旧逻辑及时清理”。
- 当前工作区有其他未提交改动；实施时将本功能分阶段、分范围提交，避免带入无关修复。本阶段的团课实现位于 `codex/segmented-schedules` 工作分支，尚未合入 `main_v2` 或部署；1-on-1 的独立规则、额度与 UI 阶段仍待实施。
