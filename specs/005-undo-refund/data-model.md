# 数据模型与状态转换

## 退款交易和收据

`receipt_record.payment_record_id` → 唯一有效负金额 `payment_record`（REFUND/REFUNDED）→ 目标课程负向 `payment_allocation`；参与人通过付款的 participant index 与订单参与人映射。行级操作定位 `(orderId, orderItemId, participantIndex, studentId)`，学生须由服务端验证。一个显示行可能合并多条购买记录，一条购买记录可能有多次退款，必须明确选中目标。仅完整撤销选中的一次行级退款；历史整单或跨行退款不得部分撤销，不能明确归属则拒绝并人工处理。收据及内部快照不向浏览器原样返回。

状态：有效退款 → 校验通过并原子撤销 → 已撤销、可审计；重复请求只能返回已处理。失败保持有效退款及关联数据原状。实施时核验逻辑删除后的审计可查询性，不能仅依赖默认过滤查询。

## 退款快照

现有 `RefundUndoSnapshot` 包含 before、after、Credit 学生/余额与处置；`RefundStateSnapshot` 包含订单、项目、参与人、课包、退款状态、付款、分摊、私教组成员、班级报名、课程实例、周期规则和时段及 Credit 账本。新快照需有可验证版本、捕获范围和完整性；完整性机制需兼容现有数据格式，不能未经设计认定旧快照完整。必须核对所有退款写入是否实际纳入快照，且 before 发生在首次写入前。

基于实体 ID 和显式业务字段计算差异，比较时规范化 BigDecimal 数值、DB 时间精度、集合顺序及 null；version 用于防并发而非机械回滚。恢复 SQL 必须能明确写回 null 和逻辑删除状态，验证更新行数；未捕获的新增相关事实也纳入提交校验。

## 课程、权益与排课

课程、课包、私教组成员、班级报名恢复各自退款前真实状态；班级报名可处于逻辑删除状态，必须通过显式安全查询和版本条件恢复。周期规则、时段、课次仅恢复该笔退款造成的状态变化；实例必须原本存在且开始时间在撤销提交时仍为未来。已发生课次、lesson record、hour ledger 不更改。共享班课实例不得因单人退费恢复或覆盖。

## Credit

关联原退款 Credit 流水与学生账户；验证余额、后续使用及安全可逆性，写入可追溯的反向流水，绝不直接覆盖历史账本。账户锁及相关写入协议需经真实数据库并发验证。

## 撤销审计

记录目标退款/收据、操作者、时间、结果和可安全展示的失败原因；成功与业务变更原子提交，失败在事务回滚后由独立可靠路径持久化。实现前评估现有审计存储是否满足可靠性和访问控制，不能假定已具备。
