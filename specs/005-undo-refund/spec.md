# Feature Specification: Data Summary 撤销退款

**Feature Branch**: `005-undo-refund`  
**Created**: 2026-11-08  
**Status**: Draft  
**Input**: 为 Data Summary Refund Student 增加安全的撤销退款功能。覆盖退款交易与收据关联、课程状态和后续排课恢复、财务/Credit 回滚、权限、并发、历史数据边界、API、前端交互与验收测试；只做规范阶段，保留现有工作区改动。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 撤销误操作退款并恢复课程 (Priority: P1)

作为有退款管理权限的工作人员，我希望从 Data Summary 的 Refund Student 区域找到一笔误操作退款并撤销，使退款前的课程状态、课包权益及后续排课恢复，避免学生因错误退款而无法继续上课。

**Why this priority**: 退款会导致课程结课，错误退款会同时影响财务、课程权益和未来排课；恢复完整业务状态是该功能的核心价值。

**Independent Test**: 使用一笔带有完整退款前后状态记录、且退款后没有其他关联变更的退款，工作人员从 Refund Student 行完成撤销，检查系统状态回到退款前并恢复被取消的后续排课。

**Acceptance Scenarios**:

1. **Given** 一笔退款已使课程结课，且退款前存在未来周期排课；**When** ADMIN 或 STAFF 在 Refund Student 中选择该退款并确认撤销；**Then** 系统以一笔退款交易为单位恢复退款前的课程、课包、订单与相关排课状态，未来可上课的排课重新出现，已发生的上课和消课历史保持不变。
2. **Given** 显示行合并多条课程购买记录；**When** 工作人员发起撤销；**Then** 系统先定位具体学生和购买记录，只撤销选中的该行退款，不恢复同订单其他课程或学生。历史整单或跨行退款不可伪装为行级退款进行部分撤销，应提示人工核查。
3. **Given** 退款已退回外部银行、现金或其他支付渠道；**When** 工作人员查看确认提示；**Then** 系统明确提示撤销只恢复内部记录，不自动追回外部资金，工作人员必须先核实线下资金处理。

---

### User Story 2 - 安全识别可撤销退款 (Priority: P1)

作为工作人员，我希望系统准确列出退款行可关联的退款交易，并在无法安全判断时阻止操作，以免撤销错误退款或产生财务与课程状态不一致。

**Why this priority**: Data Summary 的显示行可能合并多条购买记录，一条购买记录也可能有多笔退款；必须准确定位所选学生、购买记录和退款流水。历史跨行退款不得部分撤销。

**Independent Test**: 准备单笔、重复、多行影响以及缺少关联信息的退款数据，验证候选交易展示、选择和不可撤销原因。

**Acceptance Scenarios**:

1. **Given** 某行仅可靠关联一笔有效退款；**When** 工作人员打开撤销入口；**Then** 显示该退款的收据标识、时间、金额、学生/课程和影响范围，并允许继续确认。
2. **Given** 某行可靠关联多笔有效退款；**When** 工作人员打开撤销入口；**Then** 系统列出可选择的退款交易，工作人员明确选择其中一笔后才可确认，不能默认撤销不确定的交易。
3. **Given** 历史退款缺少可验证的收据、分摊或学生/课程关联；**When** 工作人员查看该行；**Then** 入口隐藏或标记为不可自动撤销，并说明需要人工核查，不猜测退款归属。

---

### User Story 3 - 在并发和权限边界下保持一致 (Priority: P1)

作为系统负责人，我希望撤销退款受到角色、并发和状态校验保护，使任何失败都不会留下部分恢复结果。

**Why this priority**: 退款是财务和课程联动操作；权限绕过、重复请求或并发覆盖都可能造成不可逆业务损失。

**Independent Test**: 使用无权限角色、重复点击、并发修改和快照不匹配数据执行撤销，验证请求被拒绝或完整回滚。

**Acceptance Scenarios**:

1. **Given** 当前用户为 MANAGER 或其他非退款管理角色；**When** 其尝试调用撤销操作；**Then** 服务端拒绝请求，且不执行任何财务、课程或排课修改。
2. **Given** 工作人员打开确认界面后，另一操作改变了订单、退款、课时或排课关联状态；**When** 工作人员提交撤销；**Then** 服务端重新锁定并校验最新状态，拒绝不安全撤销，所有本次修改回滚，并提示刷新或人工核查。
3. **Given** 用户快速重复提交同一退款；**When** 多个请求同时到达；**Then** 最多一个请求成功，其他请求被识别为已处理或并发冲突，不重复恢复、不重复生成排课。
4. **Given** 撤销过程中任一财务、课程、课包、Credit 或排课恢复步骤失败；**When** 事务结束；**Then** 整笔操作回滚，不出现只删除退款记录、只恢复课程状态或只恢复排课的部分成功。

---

### User Story 4 - 撤销后获得清晰反馈 (Priority: P2)

工作人员希望撤销完成后立即看到最新的汇总和列表状态，并能理解不可撤销的原因，以便继续处理学生业务。

**Why this priority**: 清晰反馈可避免重复点击、错误判断和绕过系统的人工修改。

**Independent Test**: 分别验证成功、用户取消、权限拒绝、快照缺失、状态冲突和排课冲突时的页面反馈及列表刷新。

**Acceptance Scenarios**:

1. **Given** 撤销成功；**When** 页面收到结果；**Then** 页面保留当前筛选条件和产品标签，刷新统计与列表，受影响行从 Refund Student 移回对应正常状态，并反映恢复后的后续排课。
2. **Given** 工作人员取消确认或撤销失败；**When** 操作结束；**Then** 页面不改变业务数据，显示可理解的原因；并发或状态变化错误触发刷新以显示最新状态。
3. **Given** 用户正在等待撤销请求；**When** 其再次点击操作；**Then** 按钮禁用并只发送一次有效请求。

### Edge Cases

- 历史整单退款可能影响多个订单项或学生；不得作为行级退款部分撤销，自动行级撤销无法安全识别时转人工核查。
- 同一课程存在多笔未撤销退款；只能选择并撤销明确识别的目标退款，成功后刷新并允许处理其他仍有效的退款。
- 退款后已经产生上课、消课、课时流水、续费、再次退款、排课调整、代课或共享排课变更；若无法证明恢复不会覆盖这些新事实，拒绝自动撤销。
- 退款前课程本就已结课、停课或没有未来排课；撤销不得凭空创建排课，只恢复快照中原本存在且仍可安全恢复的内容。
- 后续排课恢复时出现教师、学生、教室或共享资源冲突；整笔拒绝，不能仅恢复课程和财务而遗漏排课。
- 退款转入 Credit 后 Credit 已被使用或余额不足以反向；拒绝并保持原退款状态。
- 退款收据已作废、已删除、流水缺失、金额方向错误、快照缺失或快照无法解析；拒绝自动撤销并提示人工核查。
- 订单或关联记录存在逻辑删除、版本变化、空值、时间精度差异或排序差异；只有经过明确规范化并确认等价时才允许恢复。
- 实际外部退款资金状态未知；系统仍可在内部状态满足安全条件时执行，但必须在确认前提示线下核实，不能声称已追回资金。
- MANAGER 可以查看不含财务金额的汇总，但不得获得可用于撤销的退款标识或操作权限。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 在 Refund Student 区域提供行级撤销入口，以学生、课程购买记录和选定的一次行级退款为目标；不得影响同订单其他学生或课程。历史跨行退款不可部分撤销。
- **FR-002**: 系统 MUST 根据可验证的收据、退款流水、课程分摊、订单项和参与人关系建立退款交易与汇总行的关联；当关联不唯一或缺失时 MUST 阻止自动撤销并说明原因。
- **FR-003**: 系统 MUST 对每笔候选退款展示收据标识、退款时间、退款金额、目标学生及课程购买记录；一行多笔时必须明确选择。
- **FR-004**: 系统 MUST 在确认前明确提示撤销会影响整笔退款，并提示该操作只恢复系统内部记录，不会自动追回已经退到外部支付渠道的资金。
- **FR-005**: 系统 MUST 在撤销成功时恢复退款前快照中仍可安全恢复的订单、订单项、学生参与人、课程状态、课包权益、班级权益、付款分摊、Credit 及未来排课关联数据。
- **FR-006**: 系统 MUST 重新恢复退款导致取消或停止的后续周期规则、时段和课程实例；不得改写已发生的上课、消课或课时历史，不得重复生成已有排课，也不得恢复退款前不存在的排课。
- **FR-007**: 系统 MUST 在恢复未来排课前检查教师、学生、教室及共享资源冲突；存在无法安全解决的冲突时 MUST 拒绝整笔撤销并回滚全部内部修改。
- **FR-008**: 系统 MUST 保留退款前已有的停课、结课、消课和其他退款事实，只恢复本次退款实际改变且通过校验的状态，不得将所有状态粗暴设置为统一的 ACTIVE 状态。
- **FR-009**: 系统 MUST 对 Credit 退款执行可验证的反向处理；Credit 已被使用、余额不足或无法证明可逆时 MUST 拒绝撤销并保持原状态。
- **FR-010**: 系统 MUST 在提交撤销时重新读取并锁定退款、订单及相关状态，校验快照、版本、退款流水和后续变更；预览结果不得被视为提交保证。
- **FR-011**: 系统 MUST 对快照缺失、无法解析、内容不完整、状态不匹配、退款已被撤销或关联记录缺失等情况拒绝自动撤销，不得静默降级为只删除财务记录的部分回滚。
- **FR-012**: 系统 MUST 保证撤销操作具有事务一致性；任一恢复步骤失败时，财务、课程、课包、Credit、班级权益、排课和收据状态均不得留下部分修改。
- **FR-013**: 系统 MUST 仅允许 ADMIN 和 STAFF 执行撤销；服务端必须执行最终授权校验，不能只依赖前端隐藏按钮。MANAGER 的汇总数据不得包含可执行撤销所需的财务标识。
- **FR-014**: 系统 MUST 防止重复提交和并发重复恢复；同一退款最多成功一次，其他请求返回已处理或并发冲突结果。
- **FR-015**: 系统 MUST 记录足以追溯撤销操作的退款、操作人、时间、结果和失败原因；不得向浏览器返回内部退款快照内容。
- **FR-016**: 系统 MUST 在撤销成功后刷新当前 Data Summary 数据、统计和相关列表，同时保留用户当前的产品标签、日期范围及筛选条件。
- **FR-017**: 系统 MUST 对成功、用户取消、权限失败、快照问题、状态冲突、排课冲突、Credit 不可逆和并发失败提供清晰的用户可读反馈；状态变化类失败应引导刷新或人工核查。
- **FR-018**: 系统 MUST 让已有的退款收据管理入口与 Data Summary 入口使用相同的安全撤销规则，不得通过旧入口绕过快照、排课、权限或并发检查。

### Key Entities

- **退款交易**：一次实际退款业务动作，包含退款金额、支付状态、退款时间、订单关联及可能涉及的多个订单项、学生和课程。
- **退款收据**：用于识别和审计退款交易的业务凭证，关联退款交易及其内部恢复所需的受保护状态信息。
- **退款前后状态快照**：描述退款动作前后订单、课程、课包、付款分摊、Credit、班级权益和排课等状态的受保护记录，用于判断是否仍可安全恢复。
- **Data Summary 汇总行**：面向工作人员的学生/订单/课程展示行，可能关联零、一或多笔退款，不能被视为退款交易本身。
- **后续排课**：退款影响后原本应继续存在的周期规则、时段和未来课程实例；恢复时必须区分已发生历史与未来计划。
- **撤销操作记录**：记录退款撤销的目标、操作人、时间、结果及失败原因，用于追踪和问题处理。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 对具备完整且未发生后续变更的测试退款，工作人员从 Refund Student 发起撤销后，退款前课程、课包、订单和未来排课状态在一次操作内全部恢复，且已发生的上课/消课历史零条被改写。
- **SC-002**: 对所有关联不唯一、快照缺失或状态已变化的测试退款，系统自动撤销成功率为 0%，并且每次拒绝均不产生财务、课程或排课的部分修改。
- **SC-003**: ADMIN/STAFF 的成功撤销操作在正常网络条件下 3 秒内显示结果并完成列表刷新；用户可在一次确认流程中识别目标退款及其整笔影响范围。
- **SC-004**: 100% 的 MANAGER 撤销请求被服务端拒绝，且其 Data Summary 响应不包含可执行撤销所需的退款标识或内部快照信息。
- **SC-005**: 并发提交同一退款的测试中，最多 1 个请求成功，重复请求不会重复恢复排课、Credit 或付款分摊。
- **SC-006**: 在至少 95% 的有效测试场景中，工作人员可根据收据、学生、课程、金额和时间信息正确识别要撤销的退款；其余无法确认的场景必须明确转人工处理。
- **SC-007**: 撤销成功后，Data Summary 的退款行、相关统计和筛选结果在一次刷新后与后端最新状态一致，且当前用户筛选上下文保持不变。

## Assumptions

- 目标用户是已登录的内部 ADMIN 或 STAFF；系统已有身份认证和角色校验，MANAGER 仅具备受限查看能力。
- 退款撤销的业务对象是内部退款交易；外部支付渠道的资金追回不在本功能范围内，页面只负责提示和操作风险。
- 现有订单、退款流水、收据、付款分摊、课程、课包、班级权益、周期排课和课程实例数据足以支持首轮关联与恢复核验；在规范和实现阶段会再次核对实际数据字段，不无依据新增表结构。
- 退款前状态快照是允许自动恢复的必要条件；没有完整快照的历史数据默认转人工处理，而不是使用不完整的兼容回退。
- 恢复排课只针对退款实际取消或停止、且快照确认原本存在的未来排课；历史课程记录、消课记录和已发生的课时流水属于不可改写事实。
- 后端接口沿用系统统一的 `/api/v1` 响应格式和现有登录权限体系；具体接口命名、字段和错误码在技术设计阶段确定并写入 API 契约。
- 页面继续支持当前桌面管理端布局；本功能不扩展家长端、教师端或移动端。
- 当前工作区中与本功能无关的未提交修改属于其他工作，不在本功能范围内，实施时必须保留。

## Out of Scope

- 追回、冲正或确认银行、现金、信用卡等外部渠道已经完成的真实资金流转。
- 通过人工强制覆盖后续付款、上课、消课、课时流水或排课调整来实现撤销。
- 批量撤销多笔退款、修改退款金额、编辑历史收据内容或删除审计记录。
- 为解决尚未核实的历史数据关联而直接新增数据库表或执行未经审查的结构迁移。
