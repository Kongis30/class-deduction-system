## 开发风格原则

### 函数要带中文注释
所有业务逻辑函数需添加中文注释，说明函数的用途、参数含义和返回值。

**Why:** 团队成员可能包含中文用户，注释能帮助理解业务意图，尤其对于复杂的扣减规则、排课逻辑等。

**How to apply:** 在 Java 方法、TypeScript 函数、Vue 组件方法上方添加 JSDoc 风格的中文注释。

---

### 代码结构清晰整洁，不冗余
避免重复代码，提取公共逻辑，模块之间适当解耦。

**Why:** 减少维护成本，避免前后端因为重复逻辑不一致导致的对齐问题。

**How to apply:**
- 后端：一个逻辑只写一次，通过 service 复用，不在 controller 直接写业务逻辑
- 前端：跨页面共用的组件放在 `src/components/` 或 `src/modules/shared/`，不重复造轮子
- 前后端共享的枚举值/状态码统一放在一处，不要各写各的

---

### 前后端共用变量的统一命名
前后端共用的字段（如 API 响应字段、状态码、枚举值）必须保持命���一致。

**Why:** 避免前后端字段名不对齐导致的 bug，如后端返回 `order_no` 前端写成 `orderNo`。

**How to apply:**
- 字段命名遵循后端 Java 驼峰风格，前端 TypeScript 使用相同字段名（不转换风格）
- 所有枚举值（如 lesson status、package status）在 `doc/API_CONTRACT.md` 中明文定义，前端 `domain.ts` 和后端 entity 中保持完全一致
- 涉及双向联调的功能，修改字段名前先同步更新 API_CONTRACT.md 和对应的 domain/entity

---

## 数据库变更原则

### 发现字段不够用时可以调整表结构，但要慎重
数据库变更是最需要谨慎的操作，一旦生产数据落地，变更成本会成倍增加。

**Why:** 本系统涉及课时余额、缴费记录等财务相关数据，不当的表结构变更可能导致数据丢失、查询失效或破坏业务完整性。

**How to apply:**
- 调整前先在 `doc/mysql_schema.sql` 中更新建表语句，并标注变更原因和影响范围
- 涉及 nullable → NOT NULL、或字段类型变更的，必须先检查现有数据的兼容性
- 禁止删除有业务数据的列，必须删除时先确认是否已迁移完毕
- 新增字段优先使用合理的默认值，避免因缺少默认值导致历史记录不一致
- 每次表结构变更后在 `doc/DATABASE_DESIGN.md` 中更新对应说明，保持文档与代码同步

### 符合生产场景，保证系统稳定高效
代码设计要兼顾生产环境的高可用性，避免单点故障、避免在热路径上做不必要的数据库查询或循环。

**Why:** 本系统是 JIN BEST TUTORING 的核心运营系统，任何宕机或性能问题都会直接影响业务。

**How to apply:**
- 数据库操作使用合理的索引和分页，禁止全表扫描
- 事务边界要清晰，lesson 确认等复合操作必须在同一事务内完成
- Redis 用于缓存时需考虑缓存穿透和过期策略
- 危险操作（如扣减课时、调整排课）要有完整的校验和保护机制

---

### 始终围绕业务需求，保证逻辑正确、稳定、完整
技术决策必须服务于业务目标。功能交付前必须验证业务逻辑的正确性。

**Why:** 课时扣减、排课冲突、余额计算等逻辑涉及真实的财务和运营数据，错误会导致严重的业务后果。

**How to apply:**
- 交付前对照 `doc/SYSTEM_DESIGN.md` 和 `doc/DEVELOPMENT_STAGES.md` 确认功能范围和完成标准
- 每个业务操作（如课程确认、订单创建、排课生成）都要有明确的成功/失败边界
- 边界情况（余额为 0、冲突检测、重复确认等）必须有清晰的错误提示，而不是静默失败
- 涉及金额、课时数的计算逻辑必须写单元测试，覆盖正常路径和异常路径
