# 同一课程续课修复计划

> 2026-10-23。依据 [业务规则](./logical-course-renewal-business-rules.md) 与 [代码审计](./logical-course-renewal-code-audit.md)。本文是实施和验收计划；不把尚未完成的行为写成已上线能力。

## 目标与边界

一次真实续课是一条**新课程购买行**，价格和权益独立保留，但追加在当前订单内。订单继续作为统一的收据和付款归属；同一学生、Product、Teaching project、兼容计量单位及明确指定原课程来源时，新增权益接在同一逻辑课程下。运营页面显示一门课的累计权益，仍可查看各行购买价格。原报名录错才更正原行。

沿用现有 `course_package.id`（1-on-1）和 `class_enrollment.logical_course_id`（班课）作为课程身份；班课每条课程购买行保留独立 `class_enrollment`。不新增可人工维护的课程余额表，不拆分当前订单，不重写历史课次和已购价格。老师 `allocated` 只由 Edit Schedule 与既有消课规则改变。

## 一、先收紧保存入口与数据关系

1. **同一事务验证续接。** `EnrollmentOrderServiceImpl` 在当前订单内校验新增课程行，再由 `RegistrationIntakeServiceImpl` 对指定来源检查学生、Product、project、单位、来源状态、最新有效段、起始日期和班级冲突。金额依新行选定方案计算；原订单其他课程行与已收款项不被覆盖。
2. **同时写入课程身份。** 班课新建权益后，将来源课程行、新课程行的 `logical_course_id` 与新旧权益的 `logical_course_id` 统一为原链根 ID。私教继续以原 `course_package.id` 为课程身份并累加总量、余额，不改老师分配与旧课次。
3. **保护已有课程行并保留简洁入口。** `applyCorrectedItems` 不允许 Edit Receipt 移除已有课程行；Add course 创建一个新的订单行，支持选择 Product／project／Registration plan／班级／数量。相同 Product/project 的新行续接同一逻辑课程，不同选择则创建另一逻辑课程，但均留在当前订单和收据中。原行同费率增加月份按原行费率计算；费率不同则新增行按新 Registration plan 计价。Add payment 新增的流水归当前订单，保存后 Data Summary 的 View Receipt 仍打开该订单。真正需要纠正原报名填错的月份数时，明确编辑原行，并检查其后续权益。
4. **既有数据回填。** 先只读扫描已存在的班课续购链：学生、Product、project、单位、日期顺序、订单关联都唯一一致时才回填订单行 `logical_course_id`。异常链输出清单人工核对，不自动合并。迁移可重复执行；上线前后核对行数与来源 ID。不得动 `allocated`、历史消课或价格。

这一切片完成后，直接调用 API 也不能把课次续购为月份，不能用同一来源生成两条目标权益，不能在续购后改坏旧段。

## 二、提供一个课程级读取口径

在现有服务层加入一个**批量、只读**的班课汇总函数，输入相关 `class_enrollment`、有效课次记录和查询日期，输出按学生＋逻辑课程 ID 分组的课程视图。它只负责计算，不写余额，避免与购买、退款、消课各造一套真值。

- 课次：累计有效购买课次；已用沿用当前班课的“同一上课日只消耗一次 session”口径，并只计算最终有效确认；剩余为两者之差。每个课次仍保留原 `class_enrollment_id`。同一 occurrence 不能重复确认或重复扣减。
- 月份：仅有效、相邻衔接的权益段构成连续 Period；有空档时显示分段，不把未购日期算成有效。主记录显示最新有效截止日与剩余天数，不显示“剩余小时”。
- 被撤销、停止或退款的购买保留在财务历史，但其无效权益不能增加运营余额或延长有效期。若有已用课次或排课占用，先阻止不安全冲正。
- 跨实际班级时，逻辑课程身份相同，班级名单只显示该班对应时段的学生，不把旧班与新班名单混合。

`ClassGroupServiceImpl.listEnrolledStudents` 和 `listEnrolledByStudent` 使用此口径返回一条主记录及可展开的购买段。前端 `ScheduleAdjustmentsView.vue` 展示累计量和最新有效期，段详情按需展开；原逐段主列表代码随之删除。API 只增添课程 ID、累计值、段列表等必要字段，不改变点名提交所需的权益 ID。

## 三、让 Data Summary 使用同一有效权益口径

`DataSummaryServiceImpl` 仍返回逐笔购买及付款事实供月份筛选、退款、收据操作；同时为同一订单内的同一课程提供服务端计算的有效 Period／累计课时或课次。`DataSummaryView.vue` 按订单与逻辑课程显示一行，财务金额继续只汇总所选月份的购买。View Receipt 始终打开该行所属订单的原收据；同一课程的多笔购买需要退款时，才在退款窗口选择具体购买行。不同课程各显示一行，但可共用同一订单与收据。前端不再用订单快照的最早／最晚日期自行推断权益有效期；移除被替代的日期拼接逻辑。

取消、退款、停止、原单更正后重新读取，Period 与 Schedule 使用同一批有效权益。只退款金额而权益尚有效的特殊状态，必须依已有退款状态规则判定，不能靠 `paymentStatus` 一项猜测。打印、导出和不同角色视图均使用同一展示行。

## 四、保留消课归属，修复提醒与冲正边界

班课点名继续按上课 occurrence 日期定位**唯一权益段**，一学生在一次课只落一条有效确认；Undo 回到原权益段，再由读取汇总刷新课程余额。1-on-1 消课继续读取原课包，续费不生成新消课入口。

`RenewalReminderServiceImpl` 按逻辑课程取最新有效段，旧段不能在已经续费后重复提醒。对共享私教课包的多笔购买，当前退款拦截先保留；只有能按购买确定尚未消耗且未被排课占用的小时，才开放自动退回。否则继续明确拒绝并给人工核对信息，不从课包总余额猜一笔购买可退多少。

## 实施顺序与最小改动范围

| 顺序 | 主要文件／模块 | 完成标准 |
| --- | --- | --- |
| 1. 保存与保护 | `RegistrationIntakeServiceImpl`、`EnrollmentOrderServiceImpl`，必要的定向回填 SQL | 新购买行、权益与付款留在原订单；来源、单位、最新段、期限、历史更正受服务端约束。 |
| 2. 班课读取 | `ClassGroupServiceImpl`、对应响应类型、`ScheduleAdjustmentsView.vue` | 同学生逻辑课程一条主记录，课次累计余额和月份到期日准确。 |
| 3. 报表读取 | `DataSummaryServiceImpl`、响应类型、`DataSummaryView.vue` | Period 与 Schedule 一致；财务仍逐笔、按月汇总；打印导出一致。 |
| 4. 入口与周边一致性 | `RegistrationIntakeView.vue`、`RenewalReminderServiceImpl` | 原行 `+ Months` 与 Add course 都创建新购买，分别选用原方案／新方案对应的月单价；无旧段重复提醒。 |

各切片沿用已有 Mapper、实体和页面结构；确有重复的课程级计算再提取单个小型汇总组件，不新增通用框架、缓存或平行余额表。改一个旧路径就删掉相应废弃分支，避免长期并存两套算法。

## 验收与上线控制

1. 原四个月再按不同方案购买两个月：两笔订单价保留；Schedule 一条课程、有效期续接；Data Summary 一条课程且月份金额正确；旧、新期间点名分别落在对应权益段。
2. 原私教课包再买 10h：同 package ID，Total／Remaining 各增加 10h，allocated 与历史消课不变；Undo 后余额正确。
3. 按课次再买 8 节：累计购买／净已用／剩余正确；同日多时段仍按现有业务规则消耗一次 session；重复确认、Undo 不重复扣减。
4. 原行 `+ Months` 按原 Registration plan 的费率增加数量；Add course 可换 Registration plan／费率并在同一订单生成新课程行。两行价格在同一收据中清楚展示；新增付款也记入该订单。历史购买价格不因方案更新自动改写；较早课程行的更正不能改坏后续权益。
5. 调班、期限空档、错误单位、旧段再次续购、并发双提交、续后更正旧收据：按规则展示或明确拒绝，无部分写入。
6. 取消、退款、停止后：财务历史仍可查；无效权益不延长 Period，不再触发错误提醒；共享私教课包的不可安全自动退款仍被阻止。

在本地用针对性服务层与页面联调核对上述场景，再部署。若扫描发现不唯一的线上续购链，先输出记录列表，由业务核对后逐条处理；不能自动推断老师 allocated 或改写历史消课。
