# Edit Schedule 易用性改造实现计划

> 状态：实施中。当前先落地后端同周期额度调整和未来课次老师交接；预览交互与编辑窗口精简仍待实现。未修改线上数据。
> 范围：1-on-1 课包的 Edit Schedule 窗口及其保存链路。课时口径以 [1 对 1 课时业务规则](./one-on-one-hours-business-rules.md) 为基础；实施时需要同步修订其中“分配额变化必然新建周期”的旧约定。

## 1. 目标与现状

### 当前实施进度

- 后端已开始将“只改已有 slot 分配额度”与长期改排课分开：保留规则 ID 和周期起点；增加额度时补齐末尾普通课，减少额度时只回收未开始、无记录的末尾普通课。历史／待处理／人工调整课无法安全回收时阻断保存。
- 换老师时，1-on-1 Lessons 仍通过同一 slot lineage 展示完整时间线；已处理课次和原老师快照不改，未来无 lesson record 的有效课次改为新老师，保留其单次时间、教室和课程名称。
- Edit Schedule 窗口尚未完成计划中的紧凑摘要、增减课时输入、差异预览和二次确认。当前阶段先修正保存语义和提示，后续按第 4 节继续。

管理员常见的两类需求是：沿用现有每周时段，给某位老师补充或收回尚未使用的课时；从某个日期起改变固定上课安排，重新安排未来课程。用户应直接说明想改变的老师、时段和课时，不应为了增加 2h 而重填所有老师的剩余分配额，也不应猜测保存会否重置老师的消课统计。

当前 `RecurringScheduleView.vue` 的 Edit Schedule 把 Start Date、Status、Notes、整张周历及每个 slot 的 `Schedule total` 一起展示。`Schedule total` 包含本周期已消课与未处理课时；前端和后端把它的变化视为新排课周期，校验时又要求新周期分配额不超过当前可用余额。结果是“在原计划末尾增加一节课”和“彻底重排未来课程”走同一条操作路径。另有 Adjust Schedule 窗口处理单周/单课临时变化，不应在 Edit Schedule 中复制该能力。

本次改造的原则：**一个 Edit Schedule 入口、一个保存预览、由系统识别影响范围；后台对不同业务操作使用明确的写入路径。**管理员不需要选择“周期版本”等技术概念。

## 2. 用户在窗口中的操作

### 2.1 默认视图：看清现状，快速改剩余课时

窗口标题为 `Edit Schedule`，副标题显示学生、课包和当前固定上课安排。顶部只放三项与本次决策有关的课时：

| 指标 | 展示含义 |
| --- | --- |
| Package remaining | 课包账本剩余课时；不能直接等同于可新增排课时。 |
| Committed hours | 当前老师尚未最终消课的分配，加上不包含在这些分配内的其他规则预留与保留例外课次；同一课时只计一次，详情可展开。 |
| Available to add | 课包剩余扣除去重后的占用，本次可以追加到现有安排的课时；由后端计算，异常或负差异不默默归零。 |

下方按现有 slot 列紧凑行：`周几 · 时段 / 老师 / 教室 / 该时段已扣 / 该时段剩余 / 最后一节预计日期`。同一老师负责多个时段时，老师汇总只在顶部或展开详情中显示，避免把老师余额重复放在每一行。点击一行展开编辑，默认只突出两个操作：

- `调整未来课时`：输入相对变化量，例如 `+2h` 或 `-2h`；旁边即时说明预计增加/取消几节普通未来课。历史总分配额只读展示，不再让管理员直接改含历史的 `Schedule total`。
- `修改这段安排`：展开当前老师、课程名称、教室等字段。修改固定老师或每周时段会进入下文的未来重排预览；只改名称、教室或备注不会重置周期。

整张 `WeeklyTimeSelector` 默认折叠在 `修改每周上课时间或新增时段` 中。需要改长期上课日程时再展开；手机端先显示时段列表，周历作为编辑工具而不是首屏主体。Start Date 仅在“重新安排未来课程”时改名为 `生效日期` 并出现；原规则的起始日期在普通补课时只读。Status 从此窗口移出，停课/恢复沿用独立入口；Notes 折叠为可选项。

若管理员要改某一节或某一周，窗口提供 `仅调整单节/本周` 跳转现有 Adjust Schedule，并保留当前学生与课包上下文。该入口不修改固定周规则或老师分配额。

### 2.2 系统识别保存方式，预览说明后果

| 用户改动 | 窗口给出的结果 | 保存行为 |
| --- | --- | --- |
| 只改课程名称、教室或备注 | “更新未来课程资料；课时和已上课程不变” | 沿用当前周期，仅更新适用的未来课次。 |
| 固定时段与老师均不变，只给现有 slot 增减未使用课时 | “继续当前安排；预计新增/取消末尾普通课次” | 沿用当前周期，增减该 slot 的分配及其未开始的普通课次；历史 Deducted 不清零。 |
| 改固定时段、单课时长、长期任课老师，或新增/删除 slot | “从生效日期起重排未来课程” | 建新周期，按新安排生成未来课次；更换 slot 老师还须执行下文的完整记录交接。 |
| 临时改一节或一周 | 引导至现有 Adjust Schedule | 不改固定规则和周期分配。 |

底部固定显示差异预览，而不是笼统的“将重新生成课程”提示。至少列出：保存方式、生效日期、每位老师课时变化、将新增/取消的未来普通课次数与起止日期、保留的已开始/待处理/已调整课次，以及冲突或无法排满的原因。默认不展开逐节清单；点击数量可查看具体日期。按钮使用 `Preview changes` → `Confirm & save`，无改动时禁用。

预览的计算和正式保存必须共用同一业务规划器；保存时重新校验数据版本与资源冲突。预览后如有其他管理员消课、改排课或修改课包，拒绝旧预览的提交并提示刷新，不能静默保存不同结果。

### 2.3 更换某个 slot 的老师：整段课程记录交接

管理员把一个现有 slot 的固定老师由 A 改为 B，表示 B 从此接手**该 slot 对应学生和课包的完整 Lesson records 时间线**，不只是接手新生成的课。交接只覆盖被修改的 slot；同一课包其他 slot 的老师与记录不受影响。再次从 B 改为 C 时，C 接手 A、B 到 C 的同一条时间线。

| 课次类别 | 新老师 B 的 1-on-1 Lessons 中如何显示 | 课次 teacher 字段与历史 |
| --- | --- | --- |
| A 已最终消课的课次 | 原记录原封不动地显示在 B 接手的课程记录列表中，保持原日期、时长、状态和处理结果。 | 仍写 A；不改记录 ID、消课流水、实际授课老师、原周期和额度归属，不重新扣课。 |
| 已开始但尚未最终处理的 A 课次 | 同样随完整时间线交给 B 查看和继续处理，页面清楚标出该节原老师 A。 | 已有老师提交或其他处理记录时保留原老师和快照；最终审核仍按原课位、原周期计算，不把 A 的历史消课计入 B 的新周期。 |
| 生效后尚未上课、没有老师提交或管理员处理记录的有效课次 | 全部进入 B 的课程记录与后续课表。 | 该课次的计划 teacher 与新周期额度归属均改为 B；新生成的课次也写 B。若曾单独调整时间、教室或课程名称，保留这些调整，只把 teacher 与额度归属改为 B；若曾明确指定另一位代课老师，预览要点名提示该指定将被 B 覆盖。 |

已取消课次保留审计记录，不作为待迁移的有效未来课次。未来日期但已经存在提交/审核记录的异常情况，不能静默改写老师；预览指出课次并要求先处理记录或明确阻断保存。交接不复制记录，也不通过把历史 `teacher_id` 批量改成 B 来实现：1-on-1 Lessons 按 slot 的交接关系展示完整时间线。A 不再是该 slot 当前负责老师入口，但其已上课记录仍可从课包历史和审计中查询。

保存预览必须单列：`历史记录移交查看 N 节（老师字段不变）`、`待处理历史移交 N 节`、`未来课次改为 B N 节`，并列出被覆盖的单课代课安排。B 的页眉只统计新周期分给 B 的额度和之后归 B 的消课，不把列表中 A 的历史课时加到 B；课包 Total、Starting、Remaining 和已确认消课也不因老师交接而改变。

## 3. 业务边界与异常处理

1. **同周期增减课时仅处理一个或多个已有、固定定义不变的 slot。**增加时从该 slot 最后一节有效普通课之后顺延生成，不移动原有普通课、人工调整课或补课；减少时仅从末尾移除尚未开始、没有消课记录的普通课，调整后的分配额不得低于本周期已扣课时与必须保留的占用。不得删除已开始、老师已提交、待管理员处理、已确认、人工调整或正式请假补课。若可移除课时不足，明确报出可减少上限。
2. 新增课时必须来自真正未分配且未被其他规则、待处理课次或保留例外占用的额度。课包 `Remaining`、老师 `Remaining with`、未来普通课合计分别展示，不能互相代替。课时以 0.5h 整数单位计算；尾节不足常规单课时长时，沿用现有尾节规则，并在预览中显示实际时长。
3. 改固定老师或时段是**未来重排**。表单默认带入各 slot 尚未使用的课时，而不是要求用户把历史分配重新输入一遍；用户可再分配这些未使用额度。新周期老师的 `Deducted` 从新周期起计算。更换老师还必须按第 2.3 节把该 slot 全部历史记录交给新老师查看、把所有符合条件的未上课次 teacher 改为新老师；不得漏掉已人工调整但尚无处理记录的未来课次。页面必须在确认前明确提示统计变化。
4. 生效边界采用 `America/New_York` 的业务日期与时间。已开始、已记录或需保留的例外课次按现有规则保留；普通未来课次才可替换。更换老师时，未上课且无处理记录的人工调整课保留其时间等单课调整值，但 teacher 按第 2.3 节交接。跨夏令时、校区/教室与老师冲突、课包结束日期、暂停状态及共享私教组参与人，均由服务端在预览和保存时校验。不能为了凑平数字擅自改变课包余额、Starting Hours 或历史消课。
5. 暂停课包后，未来课次及旧计划按现有停课规则取消；恢复后仍需显式创建新计划，不通过 Edit Schedule 自动复活原安排。没有有效规则的课包继续使用 Create Schedule。
6. 对历史余额与老师分配不一致的课包，显示差异和可核查信息；若无法可靠计算可追加额，阻止自动追加并提示人工核对。不得通过截断负数或暗改分配额掩盖异常。

## 4. 最小实施路径

1. **统一读取与预览口径。**在现有规则详情旁返回当前课包、老师与 slot 的课时摘要，包括已扣、未处理、普通未来课和可追加课时。复用现有排课/课包计算，不在前端根据可见未来课次数猜余额。将前后端的改动分类和课次规划收敛到同一服务层；预览只计算、不写库。
2. **实现同周期增减的窄写入路径。**增加/减少现有 slot 的未用课时，保留规则 ID、`allocation_period_started_at` 和已确认历史；事务内锁定或校验相关课包/规则版本，更新分配额、生成或安全移除末尾普通课次，并记录操作者、变化量和受影响课次。与现有“重排未来课程”的写入路径分开，避免给现有 `PUT /rules/{id}` 的所有调用偷偷改语义。
3. **沿用并收紧重排路径。**现有 Edit Schedule 更新服务继续承担长期时段/老师变更；明确生效日期、带入未用额度，并用同一预览结果解释保留、重建与老师交接的课次。老师交接要同时更新有效未来课次的 teacher 快照，以及 1-on-1 Lessons 按 slot 交接关系读取完整历史的关联；历史课次和消课流水不改写。只改课程资料继续走非周期更新。前后端以明确操作类型传递意图，由后端再次验证分类，不能只靠前端判断。
4. **改造窗口。**先实现紧凑摘要与 slot 行内课时调整，再把周历、备注和重新排课字段按需展开；保留 Adjust Schedule 的单周入口。删除旧的“改 `Schedule total` 即隐式重排”的表单提示和重复分支，保持一个明确的数据模型与保存入口。
5. **同步业务文档与排课历史展示。**更新 [现有课时业务规则](./one-on-one-hours-business-rules.md) 中“分配额一变就新周期”的旧表述，补上“现有固定安排内增减未用课时”的例外；确保 1-on-1 Lessons、Schedule 详情及打印历史都能区分同周期课时调整与新周期重排。

## 5. 验收场景

- **Zhen Shen Zou：**课包 Remaining 16h，Lau 剩余 4h、Derek 剩余 10h、未分配 2h。在 Derek 行输入 `+2h` 后，预览仅多一节 2h 普通未来课；保存后 Derek Allocated 18→20h、Remaining with 10→12h、Deducted 仍为 8h；Lau 及课包账本不变，周期不重置。具体新增日期以资源/假期校验后的预览为准。
- 给现有 slot 减少 2h：只移除末尾符合条件的未来普通课，老师分配和剩余同减 2h，课包 Remaining 不变，2h 回到未分配额度；如末尾课已有记录，保存被阻止并指明原因。
- 只改教室或课程名称：已发生课程、分配额与老师 Deducted 不变；未来适用课次同步更新。
- 长期更换某个 slot 的老师：预览显示该 slot 的已消课、历史待处理和全部未上课次各有多少；保存后新老师的 1-on-1 Lessons 显示完整时间线。历史课次仍显示原老师且消课数据不变；有效未来课次都显示新老师，其他 slot 的记录不出现。单独改过时间/教室的未来课保留这些值，原先单节指定代课老师被覆盖时有明确提示；多次交接仍可看到连续历史。
- 只改固定每周时间：预览旧课次保留/取消、新课次和新周期老师额度；保存后旧历史记录不改，新的未来安排按生效日执行。
- 单节代课或某周停一次课：通过现有 Adjust Schedule 完成，Edit Schedule 的固定规则与分配统计不变。
- 两位管理员同时修改、课包暂停、余额不足、资源冲突、夏令时边界和无法排满的尾节：明确提示具体阻断原因，不产生半套课次或静默改账。

以上场景是实施时的验收依据；本次仅保存计划，未执行功能验证。
