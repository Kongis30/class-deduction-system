# 每日资金流水：需求与现状梳理

> 状态：需求文档，2026-10-25。基于 `main_v2` 当前代码梳理；本文件不代表功能已经实现。

## 1. 业务目标

管理员需要回答：“指定纽约日期，系统记录了哪些实际收款和付款？每笔由谁经手、属于谁、关联哪张订单或凭证，合计进来多少、出去多少？”

**一笔真实资金变动显示一条流水，以资金发生日归属。**报名、续课、补款只是资金发生的业务原因；订单应收、当前累计已收、欠款和课程行数量不是某一天的资金流水。报名时没有付款，日报的报名历史可以有记录，资金流水则没有入账。后续在旧订单的 Edit Receipt 中补收 $1,600，补款日增加一笔 $1,600 入账；退款 $1,000，退款日增加一笔 $1,000 出账。

本页记录**系统内有凭据的交易**，用于运营核对；它不是银行账户自动对账，也不能从订单余额倒推出当天的现金流。若希望覆盖系统尚未录入的房租、采购等支出，需要另有可审计的“其他收支”录入流程，不能自动猜测。

## 2. 当前页面和代码事实

| 环节 | 当前实现 | 对资金日报的影响 |
| --- | --- | --- |
| 页面 | `DailyRegistrationsView.vue` 标题为 Daily Registrations；显示 Operator totals、Registration history、课程行与报名保存时间，支持日期、经手人筛选和 Excel 导出。 | 当前职责是查报名保存记录。 |
| 查询 | `DailyRegistrationServiceImpl.query` 将所选日期转为纽约当天起止时间，调用 `DataSummaryService.getSummary`，再按课程行汇总应收、已收和欠款。 | 列表一行对应课程，不对应一笔付款。 |
| 日期 | `DataSummaryServiceImpl.listOrders` 以 `enrollment_order.created_at` 过滤；显示字段为 `registrationSavedAt`。 | 今天给旧订单补款，不会因为补款而出现在今天；旧报名日的“Collected”可能随之后的付款或退款变化。 |
| 经手人 | 当前筛选 `registration_operator_user_id`，Operator totals 也按报名录入人分组。 | 收付款经手人与原报名录入人可能不同。 |

| 记录更正 | Edit Receipt 按付款 ID 找原行；新增付款插入新行，更正原付款时直接更新原行，同时在 `sys_operation_log` 保存整单付款前后快照。退款收据删除会 void 并软删退款行；订单／课程删除路径也可能软删或改写付款行。 | 已有更正审计基础，但其他撤销路径不一致；仅查询当前有效行无法完整解释历史日报的改动。 |

**结论：**截图中的页面目前基本只有报名记录。它的 `Collected` 是这些报名课程**查询时的累计已收分摊值**，不是当天实收；因此不能用它来核对每日资金进出。

## 3. 页面职责与范围

页面名称、菜单名称与路由继续保持 **Daily Registrations**。页面内设 **收支流水** 和 **报名记录** 两个清楚标注的视图，默认展示收支流水；两个视图共用所选日期，但分别统计。报名记录的应收、累计已收不参与资金日报合计，也不把报名课程行与交易行混在一张金额表中。

资金流水覆盖系统当前支持的真实对外收付，并为将来新增的收支入口遵守同一归集规则。首批事件及计数规则如下：

| 业务事件 | 流水来源／触发点 | 页面显示 | 外部资金合计 |
| --- | --- | --- | --- |
| 新报名或新订单收款 | 一条有效 `payment_record`，`PAYMENT`、正数、真实支付方式 | 入账；按每笔拆分支付分别列行 | 加入入账 |
| Edit Receipt 补款／续费补缴 | 在原订单新增的 `payment_record` | 补款发生日的一笔入账，关联原订单、学生与课程说明 | 加入入账；不回填到原报名日 |
| 在订单付款入口补款 | 新增的 `payment_record` | 同上 | 加入入账 |
| Student Credit 充值，使用现金／卡等真实方式 | 充值订单下的付款记录 | “Credit 充值”入账；关联学生与充值收据 | 加入入账一次；Credit 增额台账不再加一次 |
| 退回原支付渠道的钱 | 有效 `REFUND` 付款记录，金额为负 | “退款”出账，金额以正数展示在出账列 | 加入出账 |
| 退款转 Student Credit | `REFUND` 记录的方式为 `STUDENT_CREDIT`，并有 Credit 增额 | “转入 Credit”的内部转账记录，可在流水中查看 | 不计对外出账；不再计入账 |
| 使用 Student Credit 支付课程 | `PAYMENT` 方式为 `STUDENT_CREDIT`，并有 Credit 扣减 | “Credit 抵扣”的内部转账记录 | 不计对外入账 |
| 手工调整 Credit 余额／充值冲回 | Credit 台账 | “Credit 调整／冲回”的内部余额记录 | 不计对外收支；若同时真实退钱，必须另有对应对外退款记录 |
| 教师工资 | `teacher_payment` 从 `PENDING` 确认为 `PAID`，写入 `paid_at` | “教师工资”出账，关联教师和工资单 | 加入出账一次 |
| 单纯报名、改价、改课程、生成收据、创建待支付工资单 | 无真实收付款 | 不生成对外资金流水 | 0 |

其他人工支出或收入若属于目标范围，必须先提供金额、方向、实际发生时间、支付方式、经手人、对方、用途和凭证的录入入口，并纳入同一日报。当前代码中未发现通用费用收支流水，**不能声称本页已覆盖系统外发生的所有钱款**。

## 4. 每笔流水所需信息与统计口径

### 4.1 行字段

每行至少显示：发生时间（ET）、方向和类型、入账金额、出账金额、支付方式、学生／教师或其他对象、关联课程／用途、订单号／交易号／凭证入口、经手人、备注及记录状态。金额统一显示两位小数。点击一行可查看原订单、付款、退款凭证或工资单；同一订单的多次收款必须能看到多行。

多学生订单按付款的 `participant_index` 定位学生；若旧付款没有该值，显示“订单级付款／学生待核对”，不随意挂到第一个学生。课程归属以已有付款分摊为准；没有明确分摊时显示订单级别和课程摘要，不按课程行复制完整金额。

### 4.2 日期、经手人与筛选

- 默认日期是 `America/New_York` 的今天；按交易实际发生时间归档：付款／退款取有效 `payment_record.paid_at`，教师工资取 `teacher_payment.paid_at`。页面和 Excel 都标注 ET，并正确跨越美国夏令时。记录录入时间 `created_at` 单独保留，供核查补录或回填。
- 经手人筛选针对**该笔收付款的经手人**，不使用原订单报名操作人。缺失经手人的旧记录显示“未记录”，仍进入当日合计。
- 支持日期区间、收支类型、支付方式、学生／教师、经手人、状态和关键字筛选。默认按发生时间倒序；同一时刻用来源类型与稳定 ID 排序，避免列表跳动。筛选后的合计与导出遵循相同条件。
- 手工录入实际支付日期若与保存日期不同，流水按实际支付日期显示，并在详情标注录入日期及操作者。不能因为今天保存了昨天的付款而误算到今天。

### 4.3 汇总与核对

页头显示 **入账、出账、净流入、交易笔数**，可另列“内部 Credit 流转”金额但不混入净流入。按经手人、支付方式、类型分组的合计应与明细逐笔相加一致。经手人未知也要独立成组。教师工资只有真实确认支付后的记录进入出账。

报名历史中的“课程记录数／订单数／应收／累计已收／欠款”继续保留在报名标签，并明确它们是报名或订单状态指标；资金流水不显示“当日应收 = 当日入账”的误导等式。导出 Excel 分别命名，列和汇总与页面一致。

## 5. 更正、作废与历史数据

1. **实际补收／实退：**新增独立交易，保留原交易 ID、金额、日期。Edit Receipt 加 $1,600 必须生成新付款 ID；退款 $1,000 必须有独立退款 ID。
2. **录入错误更正：**修改既有交易的金额、日期、方式或经手人时，记录更正人、时间、原因、旧值和新值。更正后的日报按正确发生日和金额显示，原日报变化能从“更正记录”解释；不能把更正当成另一笔真实入账。当前 Edit Receipt 有订单级前后快照，但日报尚不能按付款 ID 展示清晰的更正记录。
3. **撤销／删除：**保留原交易和作废行为的审计轨迹；当前有效合计排除已作废记录，历史导出可查看原始值、作废时间、操作者和原因。删除收据、订单或课程时不可使曾经发生的资金无痕消失；若钱确实退回，应另记退款，不能靠删除付款模拟退款。
4. **历史数据：**上线前按现有 `payment_record` 和已确认的教师工资回填可确认的流水。旧记录缺时间、学生、经手人、支付方式或已被改写时，标记“待核对”，不以订单创建日或当前余额臆造一笔交易。回填应按来源 ID 幂等，避免重复；来源与日报金额逐笔核对。

## 6. 实现建议与验收

先保持原 Daily Registrations 的查询和导出作为“报名历史”；新增独立的资金流水查询，读取实际付款／退款和已支付工资，并按来源 ID 去重。对 Credit 的现金与内部流转分类写成集中规则，前后端共用服务端判定结果，避免 UI 自己猜。将 Edit Receipt 更正及删除路径的审计补齐后再宣称日报可长期作为财务核对依据。不要把订单当前 `received_amount`、Data Summary 的 `paidAmount` 或收据总金额当作交易事实。

| 验收场景 | 预期结果 |
| --- | --- |
| 10 月 24 日报名收 $500 | 24 日资金流水一笔 +$500；报名历史仍有对应报名。 |
| 10 月 25 日给旧订单续费补收 $1,600 | 25 日新增 +$1,600；原报名日不新增交易，原订单和收据可追溯。 |
| 10 月 25 日退款 $1,000 到原支付渠道 | 25 日新增出账 $1,000；当日净流入相应减少。 |
| 一单用现金 $600、Zelle $1,000 分两笔付款 | 两条入账，方式分别正确；总入账 $1,600。 |
| 报名先欠款，次日补齐 | 报名日只计当日实收，次日只计补款；不重复统计累计已收。 |
| 用 $200 Student Credit 支付／退款转 Credit $100 | 显示内部流转，外部入账与出账均不增加。 |
| Credit 充值 $300 并随后消费 $200 | 充值日外部入账 $300 一次；消费只影响 Credit 余额。 |
| 工资单待支付 $800，次日确认付款 | 创建日出账 $0，确认支付日出账 $800。 |
| 更正旧付款日期或金额、撤销退款 | 各日期有效合计正确，详情可看到旧值、变动人、时间和原因。 |
| 日期跨美国夏令时切换 | 每笔落在正确的纽约业务日期，页面与 Excel 相同。 |

完成标准：指定一天的有效对外入账、出账分别等于该日符合条件的来源交易逐笔汇总；所有差异可定位到具体交易 ID、补录、更正或作废记录。不得通过课程行数量、订单快照或 Credit 内部划转补出一个看似平衡的数字。
