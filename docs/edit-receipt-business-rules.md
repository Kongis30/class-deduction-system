# Edit Receipt：原报名更正业务规范

> 状态：业务规则基线，2026-10-22。本文记录目标行为；当前实现与尚需人工核对的边界见 [更正计划及实施记录](./edit-receipt-correction-plan.md)。

## 1. 功能定位

Edit Receipt 是**更正指定的一笔原始报名**。管理员从这笔报名的收据进入，修改当时登记错、漏填或后来需要调整的报名内容；保存后仍是同一个订单，收据是订单及其关联业务数据的展示结果。

续课入口也显示在 Edit Receipt 的课程行旁，但它会打开一笔新的购买，而不是修改原订单。直接延长月数沿用原购买行的月费率；“Add course at new rate”按新选方案独立计价。两笔购买保留各自订单、收据、付款，关联同一逻辑课程；班课的逻辑课程归属保存在逐学生权益上，避免多人收据串联。Data Summary 合并为一行展示完整 Period。1 对 1 仍使用原课包 ID，老师的 allocated 只由 Edit Schedule 调整。已经续课的课程不能通过原收据更正单独改变班级或购买期限，以免破坏后续权益。共享同一个 1 对 1 课包的多张收据，现有自动退款、取消和删除会误操作整个课包，因此先明确阻断并要求人工核对；后续若要自动处理，必须建立按购买行分摊的消课和退款台账。

更正范围包括学生在本次报名中的资料、课程行、教学项目、报名方案、实际班级、Attendance、购买数量、价格和费用，以及本次报名关联的付款记录。对应的课程权益、学生未来课次和接送信息必须与更正后的报名一致。更正不得暗中影响同一学生的其他报名、续报、充值或退款。

已发生的课程和真实收付款必须保留可追溯的历史。续报、停课、实际补款、退款和已确认课次的业务调整仍走各自流程；不能通过改写一张旧收据来冒充这些事件。

## 2. 对象归属与事实来源

| 对象 | 在更正中的职责 | 规则 |
| --- | --- | --- |
| `enrollment_order` | 本次报名的身份、日期、汇总金额和状态 | 保持原订单 ID；只改这笔订单。 |
| `enrollment_order_item` | 本次购买的课程、班级、购买条款和课程金额 | 每行保持稳定 ID；新增、移除必须显式处理，不能靠前端隐藏行。 |
| 报名方案快照 | 当时可选的计费单位、数量上限、覆盖规则、Attendance 档位和价格 | 历史方案之后被停用或调价，不应使未改动的旧报名无法保存。 |
| `class_enrollment` / 1 对 1 课包 | 学生实际可使用的课程权益 | 按本次报名的有效购买条款同步；续报产生的独立权益不得被旧收据覆盖。 |
| 付款及分摊 | 实际收款和本次订单的付款归属 | 按付款 ID 识别；纠错留痕，真实资金变动另记流水。 |
| 班级课表、学生课次 | 班级的物理排课及学生参与关系 | 改班级主要调整学生参与的未来课次，不修改全班课表。 |
| 收据 | 本次报名当前可打印的凭证 | 从已提交的业务结果生成；原版本可追溯，不覆盖其他类型凭证。 |

**数量语义必须分开：**方案的数量上限、学生本次实际购买数量、权益目前累计数量是三个概念。现有 `package_quantity` 在部分路径表示方案上限，不能仅凭这个字段反推实际购买数量。更正时需要明确取得本次报名的实际购买月数或课次数；旧数据缺失时展示“待核对”，不得用当前权益数量悄悄填回原订单。

## 3. 更正范围与边界

### 3.1 学生与报名资料

- 姓名、年级、学校、家长电话、校区、报名日期、接送需求等可以更正本订单的报名快照。需要同步学生当前主档的字段，应在页面上说明；其他订单的历史快照不随之改写。
- Edit Receipt 不用于把订单转给另一位学生。多人 1 对 1 报名只可更正原有参与人的资料；更换参与人身份需独立流程。
- 空值有实际含义：取消接送、清空第二电话等必须能保存为“无”，不能因更新方法跳过 `null` 而保留旧值。

### 3.2 课程、方案、班级与数量

- 可更正本订单已有课程行的产品、项目、方案、实际班级、开始日期、购买数量和 Attendance。界面显示的每个可操作控件都必须有对应的保存语义。
- 若允许新增课程行，必须建立新订单行、权益与金额分摊；若允许移除，必须同步撤销未使用权益并处理对应付款。已有课次或退款关联时应提示受影响记录，无法安全处理时明确阻止。不能出现界面允许移除、保存后原课程仍在的情况。
- 改方案或实际购买数量时，按目标方案的计费单位、有效范围和可用课次重新校验。只改姓名、付款备注或 Attendance 时，不应因为当前方案后来改价、停用或修改上限而重新否定旧购买。
- 方案数量是上限，购买数量是本次实际选购数。月包的起止日期按所购月数计算；`2026-10-01` 起购买 2 个滚动月，在没有班级结束日期截断时到 `2026-11-30`，首尾日期均包含。日期按 `America/New_York` 的业务日期处理。

### 3.3 Attendance 与价格

- Attendance 是课程行的报名属性，可选项取决于该方案支持的 Full day、Morning、Afternoon 等档位。它与购买月数、课次数相互独立。
- 历史 Attendance 为空时，补选与原付款价格相符的档位属于**补正漏填信息**：保持原方案、购买数量、起止日期及原价，不触发“购买数量超出方案”的报错。
- 若从一个收费档位改为另一个，先展示课程金额、应收、已收和差额，再保存。优先使用原报名的价格快照；原快照不足以确定新价格时，要求明确输入或选择价格，不静默套用已变化的当前价格。
- 更正后的 Attendance 同步到订单行、对应权益、课程级接送视图和新生成的学生参与记录。已确认课次的实际出勤不因更正报名选项而改变。

### 3.4 班级与排课

- 班课更换实际班级时，先检查原班和新班的在册日期、时间冲突与已发生课次。原班已完成或已确认的课次保留历史；从明确的生效日期起，学生的未来参与关系转到新班。班级本身的教师、教室和全班物理课表不由 Edit Receipt 改写。
- 若原班已有为学生单独建立的未完成课次或接送名单，保存时要清理或迁移这些关联，使日历、班级名单和接送名单显示一致。遇到已确认或冲突课次，应给出具体日期和处理入口，不能只改权益而留下旧排课。
- 1 对 1 更正课程或课包时，已消耗课时保持不变；总课时不得小于已消耗及不可撤销的占用。现有未来排课要按新课包重新校验，能安全保留的继续关联，无法安全迁移的要求先调整排课，不能仅改课包数字。
- 续报后的旧订单不拥有新订单的权益。编辑旧收据可以更正旧订单的历史资料和金额，但不能借此缩短、重建或转移续报权益。

### 3.5 支付与账务

- 录入错误的付款方式、日期、备注或金额可作为**原记录纠错**处理，必须记录更正人、时间、原因及更正前后值；付款行按 ID 匹配，不按列表位置匹配。
- 实际新增收款、退回现金或转入 Student Credit 是新资金事件，走收款、退款或 Credit 流程。更正订单价格可以改变应收和欠款，但不能自动伪造收款或删除既有退款。
- 保存前计算课程、接送、其他费用、折扣、已收和余额；付款分摊之和与有效付款一致。若改价后已收超过应收，提示需处理的超收金额及可用操作，不暗中把旧付款改小。
- 纯 Credit 充值收据不通过 Edit Receipt 重放课程付款；充值余额及其使用历史由 Credit 台账负责。

## 4. 保存流程与一致性要求

1. **加载事实：**以选中的订单 ID 和收据 ID 加载订单、所有课程行、原始购买数量、相关权益、付款 ID、退款、已确认课次和未来排课。标记历史缺字段及互相矛盾的数据。
2. **计算差异：**逐字段区分资料补正、Attendance 更正、课程/数量变更、价格变更、付款记录纠错和真实新资金事件。前端不得因为打开旧表单或改变 Attendance 自动改写购买数量。
3. **按变化校验：**校验被修改字段及必需的一致性约束。旧方案已变化不应影响无关字段的保存；需要改变课程权益时，再检查方案有效性、班级冲突、课次占用和后续续报。
4. **展示影响：**保存前让操作员看到原值 → 新值，尤其是班级、Attendance、有效期、未来课次、应收和已收的变化。无法自动处理的课次/账务阻断并给出具体记录。
5. **一次提交：**在同一事务内更新本订单及受影响的权益、分摊和未来参与关系；提交失败全部回滚。用订单版本或更新时间防止两个管理员互相覆盖。
6. **提交后核对：**订单行实际购买数、权益购买数及有效期、收据显示、Data Summary Period 和未来学生名单应按同一业务事实对应；付款流水之和及分摊应与订单已收一致。记录完整更正审计，再提供最新收据。

历史数据原本不一致时，**无关字段仍应可更正**，但页面必须单独列出差异。不能为了补选 Attendance 就擅自把一月权益改成两个月，也不能让原有差异被通用“方案数量不符”错误掩盖。若本次同时更正购买期限，需核对原单、收款及续报/课次证据；证据明确后在同一提交中更正权益，否则给出待人工核对的具体原因。

## 5. Wenhao Ma 案例：必须覆盖的验收场景

已知记录：订单 `EO202609220020` 显示 2 months 方案、$880、开始日期 `2026-10-01`；当前在册权益却记为 1 个月、到期 `2026-10-31`。早期收据快照未保存可独立证明实际选购月数的 `purchasedMonths`。本次截图显示 Attendance 原先未选，选择 Full day（$880）后保存，页面两次提示 `The purchased quantity must fit within the selected registration plan.`

此案例包含**两个需要分别处理的问题**：

1. **漏填 Attendance：**若只补选 Full day，保存应成功；课程价仍为 $880，方案和购买数量不变，收据与课程行、权益的 Attendance 一致。原有权益数量差异以明确提示保留待核对，不成为 Attendance 更正的通用阻断。
2. **购买期限与权益不一致：**订单显示 2 months、权益为 1 month，需要核对原报名和付款证据。确认实际购买 2 个月且无班级截止或后续权益冲突时，权益应为 2 个月，结束日期为 `2026-11-30`，Data Summary Period 随之更新。不能仅凭 `$880` 或方案名称自动批量修复所有类似历史记录。

现有后端的报错来自 `validateCorrectedV2GroupSelection` 的方案/数量校验；该校验只应在项目、方案、购买条款或实际购买数量确实改变时触发。仅凭截图不能断定是哪一个提交字段被误判为变化，后续修复时需记录该次请求中的旧值、新值与触发条件。错误应指向具体课程行及具体字段，页面只显示一次。

## 6. 其他验收场景

| 场景 | 预期 |
| --- | --- |
| 只改联系人、备注或 Attendance | 原课程数量、权益期限、排课和付款保持原业务值；保存成功。 |
| 历史方案已停用/调价，未改变选购条款 | 可以更正无关字段，不以当前方案限制否定旧订单。 |
| 改实际购买月数或课次数 | 显示改前/改后的有效期和应收；同步目标权益与 Period，并检查续报和已发生课次。 |
| 换班级，原班已有已确认课次 | 历史课次仍归原班；未来学生名单归新班，无重复或孤儿课次。 |
| 1 对 1 课包已有未来排课 | 不出现排课仍占旧课包、课包却显示新课程的状态；冲突时具体阻断。 |
| 更正付款方式/金额或实际补款 | 纠错保留前后值与付款身份；真实补款产生新流水，不重写旧退款。 |
| 新增、移除课程行 | 页面与后端同时支持并完成关联数据处理，或同时禁止并解释原因。 |
| 续报后编辑旧收据 | 新续报权益及其未来计划不被旧订单改写。 |
| 两人同时编辑同一订单 | 后提交者收到冲突提示并重新加载，不覆盖先提交者。 |

## 7. 当前实现与规范的已知差距

- 班课更正会更新 `class_enrollment`，1 对 1 更正会更新课包；现有流程没有完整处理与其关联的未来学生课次或 1 对 1 排课。
- 付款更正按排序位置复用旧付款行，无法可靠识别用户调整顺序后的原付款。
- 前端更正态显示移除课程行控件；后端只处理提交的既有订单行，省略的行不会被删除，新增行又缺少原订单行 ID。
- 收据同步会改写同订单的所有收据快照；目标行为是保留可追溯的原版本，并避免更正原报名时改写独立退款凭证。
- 数量校验以 `package_quantity`、收据快照的 `purchasedMonths` 和当前权益数量互相回退；历史快照缺字段时含义不稳定。Attendance 更正报“购买数量不符”暴露了这个问题，尚需结合实际请求体定位直接触发项。

上述差距是后续实现清单，不授权自动修改历史订单或线上数据。开发完成后按第 5、6 节验收，尤其要覆盖历史数据缺字段、既有数量差异和后来续报的订单。
