# Registration 与 Edit Receipt 功能业务逻辑梳理

> 日期：2026-10-30。本文区分已确认的目标业务规则和当前代码的实现情况；目标规则不是已完成的功能承诺。既有详细规则参见 [Edit Receipt 原报名更正规范](./edit-receipt-business-rules.md)。

## 1. 页面职责

- **Registration** 创建一笔报名订单：选择学生、课程与报名条件，登记费用、折扣和付款，保存后建立对应订单、报名权益、收据及相关业务记录。
- **View Receipt** 展示该订单当前报名与账务信息，供查看和打印。退款等独立凭证有各自的资金事实。
- **Edit Receipt** 修改所选的同一笔报名订单：页面先展示当前订单的完整情况，用户再更正或调整课程、接送、费用、折扣、付款及其他报名信息。保存后更新原订单及受影响的关联业务；不是另建一笔订单，也不能将其他订单的数据当作本单的隐藏输入。

页面中显示的课程价格、课程应付、订单应付、已付与余额应有清晰名称和可见的计算明细。订单当前事实与审计历史各司其职：历史记录可追溯，但不能在用户修改后暗中重新作为当前费用生效。

## 2. 信息与金额口径

| 信息 | 定义与编辑要求 |
| --- | --- |
| 学生及报名信息 | 本单的学生、联系方式、校区、报名日期等。涉及学生主档同步时，应明确影响范围，不能改写其他订单的历史报名快照。 |
| 课程行 | 本单购买的产品、教学项目、报名方案、班级、开始日期、数量、Attendance 及课程价格。课程价格是课程本身的金额。 |
| 接送及其他费用 | 当前订单中明确登记的各课程接送费和其他费用。选择接送且 Fee 为 0 就计 0；取消服务后对应费用不计入。历史有效费用须恢复到可见且可编辑的项目，不能隐藏。 |
| 折扣 | 当前订单及课程对应的折扣，按其归属参与应付计算。 |
| 支付 | 本订单关联的实际付款记录及其课程/参与人分摊。允许新增付款和更正已有付款；真实退款或 Credit 变化保留其独立台账。 |

课程应付按该课程价格加上明确归属该课程的有效费用、减去该课程折扣计算。订单应付为各课程应付之和及订单中明确展示的其他应付项目；订单余额为应付减去有效已付。退款、充值及多人分账按对应账本单独核对，不能重复计入。已付大于应付时显示超收或负余额，不能自动改小付款。

例如课程 $3,499、折扣 $400、接送费 $0、无其他费用时，应付为 $3,099；仅勾选或取消一项收费为 $0 的接送服务，不应让应付改变。价格 $699 与应付 $879 的差额必须能在费用、折扣或明确的分摊明细中解释。

## 3. Edit Receipt 的目标操作及关联处理

### 3.1 修改或增加课程

- 可以修改原课程的产品、项目、方案、班级、开始日期、数量、Attendance 和价格，也可以在原订单增加课程。选项、数量或价格变化后，课程金额、应付及余额及时重算；手动价格与方案标准价的区别应明确。
- A 课程改为 B 时，更新该订单课程行及其所属报名权益；取消 A 对该学生不再适用的未来参与或私教未来排课，并按 B 的实际班级或排课安排建立相应参与和计划。班课的共享物理课表属于班级，不能因一个学生换课而取消全班课次。
- 保留已发生、已确认的课次及其消费、出勤和原归属，避免重复消课；处理未来课次时区分未发生和已经处理的记录。涉及后续续报、共享权益、时间冲突或无法自动确定的记录，应展示具体影响和处理方式，不能静默迁移或改写其他订单。
- 课程/报名选择变化需要同步学生名单、日历、接送名单、Data Summary、课包或班课权益和收据。1 对 1 已消课与老师排课分配遵守现有课包与排课周期规则，不能把编辑报名当作自动重新分配老师课时。

### 3.2 修改接送及其他费用

- 允许从无到有添加接送，也允许取消、改地址和改费用；课程级需求、金额及相关接送名单一起更新。费用按页面显示的当前值计算，明确输入的 0 和取消状态必须能保存。
- 旧订单如只有订单级费用，加载时根据可靠来源恢复并明确展示；无法确定其归属时提示核对，不能靠勾选状态在不同隐藏来源之间切换。未改动的有效费用不丢失，也不能重复计费。

### 3.3 修改支付与其他信息

- Add payment 新增本订单的付款流水；更正已有付款按稳定付款 ID 更新金额、方式、日期等，记录更正前后信息。实际新增收款应新增流水，实际退款或转 Credit 使用对应账务流程。
- 单独修改课程或费用不改变既有付款；用户同时明确修改付款时按用户选择更新。课程价格、付款和分摊变更后，订单及课程应付、已付、余额、收据和相关报表应一致。
- 可以更正本次报名的其他可编辑信息。清空和取消是有效操作，保存后不能被旧快照恢复。涉及多人报名时，参与人和费用归属要明确，避免更改其他人的权益或账务。

## 4. 加载、预览和保存

1. 以订单及其关联明细、权益和付款为基础加载当前值；历史凭证作为有来源的兼容数据使用，缺失或冲突时明确提示，不能根据金额猜测并静默覆盖。
2. 编辑时将所选课程、费用、折扣、付款及变化后的影响展示在页面；金额实时重算。未改动的字段保留当前值，明确的 0、空值和 false 不能被当作缺失。
3. 保存前针对实际变动校验班级、权益、排课和账务；对无法自动处理的具体冲突展示原因及相关记录。原有历史差异不应让无关字段的正常更正被笼统阻断。
4. 保存时更新原订单及所需关联记录，确保成功全部生效、失败全部回滚；并发修改应检测版本冲突。留存操作者、时间和前后变更，保存后重新读取订单，核对收据、金额和下游业务。

## 5. 已检查的当前实现与差距

以下结论来自当前代码静态检查，个案中的历史金额来源仍需结合订单数据核实。

1. 注册与编辑共用 `RegistrationIntakeView.vue`。课程表价格读取课程价格；付款区课程 Due 使用课程价格加费用分摊减折扣，因此两处名称不同，不一定应相等，但页面缺少足够清晰的差额说明。
2. `hasExplicitCourseFees` 依据是否勾选课程接送或存在正数其他费用切换计算来源。Edit Receipt 取消最后一个相关勾选后，可能重新启用订单级历史接送费或其他费用，导致显示为 $0 的服务切换时 Due 反而增加；提交也可能携带这套旧订单级费用。截图中的 $300 是否具体来自旧接送费或其他费用，需要查该订单才能确定。
3. 历史接送回填中存在按正数取值及将课程金额 `<= 0` 视作需要旧金额兜底的处理，明确的 $0 可能被旧金额覆盖，需要按字段是否存在区分。
4. 后端更正接口更新原订单、课程、付款和收据，具有订单版本检查及更正审计；实际行为需按不同课程与付款场景分别核实。
5. 当前后端对换班已有未来学生课次、课程存在其他购买，以及团课与私教互换等情况存在明确限制；与第 3 节用户希望的直接修改及关联更新相比，尚有差距，不能假定这些场景已经自动迁移。
6. 当前旧规范对已有课程行移除、共享订单追加课程及后续权益设置了限制。这些属于现有实现边界，不能被误认为用户已取消修改本单课程的需求；涉及已使用权益或其他订单时需设计具体处理。

## 6. 验收场景

- 无接送 → 添加接送 Fee $0 → 取消 → 再勾选 → 保存并重新打开：应付始终按可见费用计算，接送状态和名单一致。
- 修改有历史接送费的订单：原有效费用可见；设为 0 或取消后保存，不因旧字段重新出现；无关课程及订单不变。
- 改课程 A 为 B：旧课程未来学生参与正确取消或迁移，目标报名和安排正确，已处理历史保留；班级共享课程及其他学生不受影响。
- 同一订单连续修改课程、接送、折扣并新增付款：课程小计、各费用、折扣、应付、已付和余额逐步及保存后均一致；旧付款不被隐式修改。
- 手动更正已有付款及新增实际付款：付款 ID、金额、日期、分摊与审计正确；退款和 Credit 账本不被隐式改写。
- 存在多个课程、多人参与、续报、历史缺字段或并发编辑时：不重复收费、不串单，冲突及无法推断的信息可见，失败不留下部分更新。
